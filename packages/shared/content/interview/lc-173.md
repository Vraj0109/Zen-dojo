## Clarify first

- What traversal order must the iterator yield? (In-order traversal: visiting values in strictly ascending sorted order).
- What operations must be supported? (`next()` returning the next integer, and `hasNext()` returning a boolean).
- What are the time and space constraints? (`next()` and `hasNext()` should run in $O(1)$ amortized time, using $O(h)$ auxiliary memory where $h$ is tree height, rather than $O(n)$ space).
- Is `next()` ever called when `hasNext()` is false? (Standard API assumption is that calls to `next()` are valid).
- What are the tree size bounds? ($1 \le n \le 100,000$, with at most $100,000$ calls).

## Examples to say out loud

- Standard BST: `root = [7, 3, 15, null, null, 9, 20]`.
  - In-order sequence is: `3, 7, 9, 15, 20`.
  - First `next()` yields 3.
  - Second `next()` yields 7.
  - `hasNext()` returns `true`.
  - Calling `next()` three more times yields 9, 15, 20.
  - Final `hasNext()` returns `false`.
- Single node tree: `root = [1]`. Initial `hasNext()` is `true`, `next()` returns 1, subsequent `hasNext()` is `false`.

## Brute force

A naive approach runs a full in-order traversal in the constructor, flattening the entire BST into an array or queue of size $n$. `next()` simply pops the next element from the array in $O(1)$, and `hasNext()` checks if the index is within bounds. While time complexity is $O(1)$ per operation, this requires $O(n)$ extra memory upfront. For a tree with $100,000$ nodes, allocating memory for all nodes defeats the purpose of an iterator, which should stream elements lazily using only $O(h)$ space ($O(\log n)$ on balanced trees).

## The key observation

Instead of flattening the entire tree upfront, we can pause the iterative in-order traversal using an explicit stack of node pointers.
In recursive in-order traversal:
1. We first walk as far left as possible, pushing nodes onto the recursion call stack.
2. The leftmost node is the smallest unvisited element.
3. When that node is popped and visited, its right subtree is explored by walking as far left as possible in the right child.
By maintaining this exact call stack explicitly, the stack contains at most $h$ nodes at any point in time. Each node in the tree is pushed onto the stack exactly once and popped exactly once across all $n$ calls to `next()`, giving amortized $O(1)$ time per operation.

## Optimal approach

1. Maintain an internal stack of node pointers `st`.
2. Define a helper method `pushLeft(node)`:
   - While `node != nullptr`:
     - Push `node` onto `st`.
     - Advance `node = node->left`.
3. Constructor `BSTIterator(root)`:
   - Call `pushLeft(root)`. The top of the stack is now the smallest element in the BST.
4. Operation `next()`:
   - Pop `curr = st.top()`.
   - Call `pushLeft(curr->right)` to load the left spine of the right subtree.
   - Return `curr->val`.
5. Operation `hasNext()`:
   - Return `!st.empty()`.

Complexity:
- Time: $O(1)$ amortized time for `next()`, strictly $O(1)$ worst-case time for `hasNext()`. Across $n$ calls to `next()`, exactly $n$ nodes are pushed and popped, totaling $2n$ stack operations.
- Space: $O(h)$ auxiliary space where $h$ is the height of the BST ($O(\log n)$ on balanced trees, $O(n)$ in the worst-case skewed tree).

## Code walkthrough

In the reference implementation:
- `stack<TreeNode*> st;`: stores the ancestor path currently being traversed.
- `void pushLeft(TreeNode* node)`: traverses down the left spine, pushing every ancestor so smaller keys precede larger keys.
- `BSTIterator(TreeNode* root)`: prepares the iterator pointing before the first element by loading the root's left descendants.
- `TreeNode* curr = st.top(); st.pop(); pushLeft(curr->right);`: consumes the in-order predecessor and advances down the successor's left branch.
- `bool hasNext() { return !st.empty(); }`: tests whether any unvisited nodes remain.

## Test it out loud

- Right-skewed tree: `1 -> 2 -> 3`.
  - Constructor pushes 1.
  - `next()` pops 1, pushes 2, returns 1.
  - `next()` pops 2, pushes 3, returns 2.
  - `next()` pops 3, stack empty, returns 3.
  - `hasNext()` returns `false`.
- Left-skewed tree: `3 -> 2 -> 1`.
  - Constructor pushes 3, 2, 1 (stack size 3).
  - First `next()` pops 1, right is null, stack has `[3, 2]`. Returns 1.
  - Subsequent calls pop 2 then 3.

## Follow-ups

- Can we implement `prev()` / bidirectional BST iterator?
  Yes, maintain two stacks or pointers, allowing backward steps by traversing right-spines instead of left-spines.
- How to achieve $O(1)$ extra memory?
  Morris Traversal modifies the tree by creating temporary predecessor thread pointers, achieving $O(1)$ space, but mutates tree pointers during traversal.
- How does this pattern apply to general binary trees (not BST)?
  The exact same stack-based in-order traversal works on any binary tree; on a BST it yields elements in sorted order.

## Common mistakes

- Flattening the tree into an array in the constructor, violating the $O(h)$ memory constraint.
- Forgetting to call `pushLeft(curr->right)` after popping a node in `next()`, missing all right-hand descendants.
- Pushing all children rather than only the left-leaning descendants.
