## Clarify first

- Does the cooling period `n` apply between different tasks, or only identical tasks? It applies only between two executions of the *same* task letter (at least `n` other tasks or idle intervals must intervene).
- Can tasks be executed in any order? Yes, any task ordering is permitted to minimize overall time.
- What if `n = 0`? No cooldown is required, so the answer is simply `tasks.length`.
- What are the constraints? `tasks.length` is between 1 and 100,000, `tasks[i]` is an uppercase letter A-Z, and `0 <= n <= 100`.

## Examples to say out loud

- Cooldown with idle slots: `tasks = ["A", "A", "A", "B", "B", "B"], n = 2`.
  - Max frequency is 3 (`'A'` and `'B'`).
  - Layout: `A -> B -> idle -> A -> B -> idle -> A -> B`.
  - Total time units = 8.
- Ample different tasks (no idle slots needed): `tasks = ["A", "A", "A", "B", "C", "D", "E"], n = 2`.
  - Layout: `A -> B -> C -> A -> D -> E -> A`.
  - Total time units = 7 (which equals `tasks.length`).
- Single task: `tasks = ["A"], n = 5`. Only takes 1 unit.

## Brute force

A simulation approach maintains a max-heap of available task counts and a queue of cooling tasks with their available timestamps. At each time tick, pop the most frequent available task from the heap, decrement its count, and if count > 0, schedule it in the cooldown queue for `time + n + 1`. While this simulation is correct and takes `O(\text{total units} \log 26)`, the total time units can be computed directly in `O(1)` mathematical steps once frequencies are counted.

## The key observation

The task(s) with the highest frequency `f` dictate the structural framework. If a task appears `f` times, it divides the schedule into `f - 1` blocks, each requiring at least `n + 1` time slots (1 slot for the task plus `n` cooling slots), followed by a final trailing block containing only the peak frequency tasks.
Let `ties` be the count of tasks that share the maximum frequency `f`.
The minimum frame required is `(f - 1) * (n + 1) + ties`.
If there are enough other tasks to fill all idle slots, no idle time is needed, and the answer is simply `tasks.length`. Hence, the answer is `max(tasks.length, (f - 1) * (n + 1) + ties)`.

## Optimal approach

1. Count the occurrences of each letter `'A'` through `'Z'` in an array of size 26.
2. Find the maximum frequency `f = max(cnt)`.
3. Count how many distinct letters have frequency equal to `f` (`ties`).
4. Calculate the frame size: `empty_frame = (f - 1) * (n + 1) + ties`.
5. Return `max((int)tasks.size(), empty_frame)`.

Complexity:
- Time: `O(m)` where `m` is `tasks.length` (counting frequencies takes `O(m)`, and scanning 26 letters takes `O(1)`).
- Space: `O(1)` auxiliary space for the fixed 26-element frequency table.

## Code walkthrough

In the reference implementation:
- `int cnt[26] = {0}; for (auto& t : tasks) cnt[t[0] - 'A']++;`: tallies frequencies of all 26 task characters.
- `int f = *max_element(cnt, cnt + 26);`: identifies the peak task frequency that constrains the schedule.
- `for (int c : cnt) if (c == f) ties++;`: counts how many tasks tie for the maximum frequency.
- `return max((int)tasks.size(), (f - 1) * (n + 1) + ties);`: returns either the geometric frame size or total task count if idle slots are completely consumed.

## Test it out loud

- `tasks = ["A", "A", "A", "B", "B", "B"], n = 2`:
  - `f = 3`, ties for 3 are `'A'` and `'B'` -> `ties = 2`.
  - Frame: `(3 - 1) * (2 + 1) + 2 = 2 * 3 + 2 = 8`.
  - `max(6, 8) = 8`. Output is 8.
- `tasks = ["A", "B"], n = 0`:
  - `f = 1, ties = 2`.
  - Frame: `(0) * (1) + 2 = 2`.
  - `max(2, 2) = 2`. Output is 2.

## Follow-ups

- How would you reconstruct the actual schedule order of tasks?
  Use a greedy simulation with a max-heap and round-robin cycle of size `n + 1`, picking the most frequent available tasks in each cycle.
- What if tasks have different execution durations?
  This becomes identical to multiprocessor job scheduling, requiring greedy heuristics or approximation algorithms.

## Common mistakes

- Simulating step by step with idle ticks when a closed-form formula answers the question in `O(m)` time.
- Forgetting that multiple tasks can tie for the maximum frequency `f` (failing to include `ties` in the final block).
- Overlooking the case where `tasks.length` exceeds the frame size, returning an answer smaller than the total number of tasks.
