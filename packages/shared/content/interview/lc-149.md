## Clarify first
- Are all input points guaranteed to be distinct? Yes, constraints specify distinct points.
- Can coordinates be negative? Yes, coordinates range from `-10000` to `10000`.
- What is the minimum number of points? `points.length >= 1`. If `n <= 2`, all points trivially lie on the same line.
- Should we use floating-point slope representation? No, floating-point slopes suffer from precision issues; reduced rational pairs `(dx / gcd, dy / gcd)` are preferred.

## Examples to say out loud
- Consider `points = [[1, 1], [2, 2], [3, 3]]`:
  - Slopes between all pairs are equal (1 / 1).
  - All 3 points lie on the line `y = x`. Return 3.
- Consider `points = [[1, 1], [3, 2], [5, 3], [4, 1], [2, 3], [1, 4]]`:
  - Anchor at `[1, 4]`, `[2, 3]`, `[3, 2]`, `[4, 1]` all form a line with slope `-1 / 1`.
  - Max points on that line is 4.
- Consider `points = [[0, 0]]`:
  - With a single point, the answer is 1.

## Brute force
A brute-force solution checks all triples of points `(i, j, k)`. Three points `(x1, y1)`, `(x2, y2)`, and `(x3, y3)` are collinear if `(y2 - y1) * (x3 - x1) == (y3 - y1) * (x2 - x1)`. Scanning all triples takes `O(n^3)` time. For `n = 300`, `300^3 = 2.7 * 10^7` operations, which can be optimized to `O(n^2)` by fixing an anchor point.

## The key observation
If we fix one point `points[i]` as an anchor, any other point `points[j]` defines a line with direction vector `(dx, dy) = (x_j - x_i, y_j - y_i)`. Two points `j` and `k` lie on the same line through `i` if and only if their direction vectors have the exact same reduced fraction representation. By dividing `dx` and `dy` by their greatest common divisor and fixing a canonical sign convention, we can count points sharing the same direction from `i` using a hash map in `O(n)` time per anchor.

## Optimal approach
1. If `n <= 2`, return `n` immediately.
2. Maintain a global maximum `best = 1`.
3. Loop through each point `i` from `0` to `n - 1` as the anchor:
   - Create a hash map or ordered map `cnt` mapping direction pair `(dx, dy)` to point counts.
   - Loop through points `j` from `i + 1` to `n - 1`:
     - Compute `dx = x_j - x_i` and `dy = y_j - y_i`.
     - Compute `g = gcd(abs(dx), abs(dy))`.
     - Divide `dx /= g` and `dy /= g`.
     - Normalize signs: if `dx < 0` or (`dx == 0` and `dy < 0`), set `dx = -dx` and `dy = -dy`.
     - Increment `cnt[{dx, dy}]` and update `best = max(best, cnt[{dx, dy}] + 1)`.
4. Return `best`.

Complexity:
- Time: `O(n^2)` time because there are `n` anchor points and `n` iterations for each anchor, each computing a `gcd` in logarithmic time on small coordinate differences.
- Space: `O(n)` space to store the slope counts in the map for each anchor.

## Code walkthrough
- `if (n <= 2) return n;` handles small inputs directly.
- Outer loop fixes anchor `i`, inner loop scans `j > i` avoiding duplicate pairs.
- `int g = __gcd(abs(dx), abs(dy));` finds the common factor to reduce fractions.
- `if (dx < 0 || (dx == 0 && dy < 0))` establishes a canonical orientation so opposite directions along the same line map to the same key.
- `best = max(best, ++cnt[{dx, dy}] + 1);` counts the anchor itself (`+ 1`) alongside all collinear points found so far.

## Test it out loud
- Test single point `[[0, 0]]`: `n = 1 <= 2`, returns 1.
- Test vertical line `[[0, 0], [0, 1], [0, 2], [1, 5]]`:
  - With anchor `[0, 0]`, points `[0, 1]` and `[0, 2]` give reduced direction `(0, 1)`. Count is 2, adding anchor gives 3.
  - Point `[1, 5]` gives direction `(1, 5)`, count 1.
  - Maximum returned is 3.
- Test horizontal line `[[0, 0], [1, 0], [2, 0], [3, 1]]`: Direction `(1, 0)` counted twice, returns 3.
- Test square `[[0, 0], [1, 1], [0, 1], [1, 0]]`: No 3 points collinear, returns 2.

## Follow-ups
- How would we handle duplicate points if the constraints allowed them?
  - Count duplicate points at the same coordinate separately for each anchor and add that duplicate count to the maximum slope count.
- Can this problem be solved in `O(n^2)` without `gcd`?
  - Cross products can verify collinearity, but grouping points into lines efficiently still requires a canonical slope representation.

## Common mistakes
- Using floating point `dy / dx` as a hash map key, which suffers from precision loss, `-0.0` vs `+0.0`, and vertical line division by zero.
- Forgetting to normalize negative signs, causing `(1, -2)` and `(-1, 2)` to be treated as different slopes even though they represent the same line.
