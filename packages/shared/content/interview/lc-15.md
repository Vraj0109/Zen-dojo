## Clarify first

- Can the same array element be used multiple times in a single triplet? No, the three values must come from distinct indices.
- Are duplicate triplets allowed in the output? No, the result must contain only unique value triplets `[a, b, c]`.
- Does the order of triplets or the order of values within each triplet matter? No, any order is acceptable.
- What if the input array has fewer than 3 elements? Return an empty list.

## Examples to say out loud

- Standard array with duplicates: `nums = [-1, 0, 1, 2, -1, -4]`.
  - Sorted: `[-4, -1, -1, 0, 1, 2]`.
  - Fix `-1` (first occurrence): finding two sum for complement `1` yields `(-1, 2)` and `(0, 1)`.
  - Triplets formed: `[-1, -1, 2]` and `[-1, 0, 1]`.
- All zeros: `nums = [0, 0, 0]`. Exactly one valid triplet: `[[0, 0, 0]]`.
- No valid triplet: `nums = [0, 1, 1]`. Sum is positive, return `[]`.

## Brute force

A brute-force solution checks all possible triplets `(i, j, k)` with `0 <= i < j < k < n`. For each combination, it checks if `nums[i] + nums[j] + nums[k] == 0`. To prevent duplicates, each triplet must be sorted and placed into a hash set. Generating all triplets takes `O(n^3)` time, which for `n = 3,000` is `2.7 * 10^{10}` operations, far too slow.

## The key observation

Sorting the array first transforms the problem: for each fixed element `nums[i]`, the problem reduces to finding two numbers to the right of `i` that sum to `-nums[i]`. With the array sorted, this two-sum subproblem can be solved in linear time `O(n)` using two converging pointers. Furthermore, sorting clusters identical values together, making duplicate avoidance trivial by skipping adjacent equal elements.

## Optimal approach

1. Sort the array `nums` in non-decreasing order.
2. Iterate `i` from 0 to `nums.length - 3`:
   a. If `nums[i] > 0`, break early (since the array is sorted, any two numbers to the right will also be positive, making a sum of 0 impossible).
   b. If `i > 0` and `nums[i] == nums[i - 1]`, continue (skip duplicate values for the first element).
   c. Set two pointers: `l = i + 1` and `r = nums.length - 1`.
   d. While `l < r`:
      i. Calculate `s = nums[i] + nums[l] + nums[r]`.
      ii. If `s < 0`, increment `l`.
      iii. Else if `s > 0`, decrement `r`.
      iv. Else (`s == 0`), add `[nums[i], nums[l], nums[r]]` to the output. Increment `l` and decrement `r`, then advance `l` past duplicates of `nums[l]` and decrement `r` past duplicates of `nums[r]`.
3. Return the collected triplets.

Complexity:
- Time: `O(n^2)` because sorting takes `O(n log n)` and the outer loop runs `n` times with an `O(n)` two-pointer inner scan.
- Space: `O(1)` auxiliary space (ignoring sorting memory and output storage).

## Code walkthrough

In the reference implementation:
- `sort(nums.begin(), nums.end());`: orders elements to enable the two-pointer sweep and deduplication.
- `if (i > 0 && nums[i] == nums[i - 1]) continue;`: skips identical candidate anchors.
- `long long s = (long long)nums[i] + nums[l] + nums[r];`: computes sum with 64-bit precision to prevent overflow.
- `while (l < r && nums[l] == nums[l - 1]) l++;`: skips duplicate left candidates once a match is found.
- `while (l < r && nums[r] == nums[r + 1]) r--;`: skips duplicate right candidates.

## Test it out loud

- `nums = [0, 0, 0, 0]`:
  - `i = 0` (`nums[0] = 0`): `l = 1, r = 3`. Sum is 0. Add `[0, 0, 0]`.
  - Pointers advance past remaining zeros (`l` reaches 3, `r` reaches 1). Loop ends.
  - `i = 1`: `nums[1] == nums[0]`, continue.
  - Returns `[[0, 0, 0]]`.
- `nums = [-2, 0, 1, 1, 2]`:
  - `i = 0 (-2)`: `l = 1 (0), r = 4 (2)`. Sum is 0. Add `[-2, 0, 2]`. Next `l = 2 (1), r = 3 (1)`. Sum is 0. Add `[-2, 1, 1]`.
  - Next `i`: `nums[1] = 0`. `l = 2 (1), r = 4 (2)`. Sum is 3 > 0, `r` moves down.
  - Done.

## Follow-ups

- How would you generalize this to 4Sum (LeetCode 18) or k-Sum?
  Use recursion to reduce `k-Sum` down to `2-Sum` at depth `k - 2`, yielding `O(n^{k - 1})` time.
- What if the array cannot be sorted or modified?
  Use a hash set to collect seen elements, which requires `O(n)` extra memory per search.

## Common mistakes

- Deduplicating `nums[i]` using `nums[i] == nums[i + 1]` instead of `nums[i] == nums[i - 1]`, which accidentally skips valid triplets containing duplicate values like `[-1, -1, 2]`.
- Forgetting to skip duplicate `l` and `r` pointers after finding a zero-sum triplet, leading to duplicate entries in output.
- Missing the early break optimization when `nums[i] > 0`.
