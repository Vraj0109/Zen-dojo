## Clarify first

- What is the eviction policy? (When the cache exceeds capacity, evict the key with the smallest use count. If multiple keys have the same smallest frequency, evict the least recently used among them).
- What operations count as an access / use of a key? (Both `get` and `put` increment the frequency count of the targeted key).
- What is the initial use count of a newly inserted key? (Newly inserted keys start with an access count of 1).
- What happens when `capacity == 0`? (Nothing is ever stored; `get` returns -1 and `put` is a no-op).
- What is the time complexity requirement? (Both `get` and `put` must run in strict $O(1)$ average time).

## Examples to say out loud

- Tie-breaking by recency: `capacity = 2`.
  - `put(1, 1)`, `put(2, 2)`: Both have `count = 1`. Key 1 is older than key 2.
  - `get(1)`: Returns 1, key 1's count becomes 2.
  - `put(3, 3)`: Eviction candidate is key with lowest frequency. Key 2 has `count = 1`, key 1 has `count = 2`. Key 2 is evicted.
  - `get(2)`: Returns -1.
  - `get(3)`: Returns 3, key 3's count becomes 2.
  - `put(4, 4)`: Keys 1 and 3 both have `count = 2`. Key 1 was accessed longer ago, so key 1 is evicted.

## Brute force

A naive implementation maintains a hash map of keys to values, along with frequency counters and access timestamps. On each `get` or `put`, updating the frequency and timestamp takes $O(1)$. However, when evicting at full capacity, scanning all elements to find the minimum frequency (and minimum timestamp for ties) takes $O(\text{capacity})$ time. Using a min-heap allows $O(\log n)$ updates and eviction, but still fails the required $O(1)$ time complexity.

## The key observation

To achieve $O(1)$ time across both frequency and recency:
1. Group keys by frequency: maintain a hash map `byCount` where each frequency `cnt` maps to its own **doubly linked list** of keys.
2. Inside each frequency list, keys are naturally ordered by recency (head is MRU, tail is LRU).
3. Maintain a single integer `minCount` tracking the globally minimum frequency.
When a key is touched, its frequency increments from $c$ to $c + 1$. We unlink it from list $c$ and prepend it to list $c + 1$ in $O(1)$. If list $c$ becomes empty and $c == \text{minCount}$, then `minCount` simply increments to $c + 1$. When adding a new key, `minCount` resets to 1. Eviction simply removes the tail node from list `byCount[minCount]`.

## Optimal approach

1. Data structures:
   - `struct Entry { int value, count; list<int>::iterator pos; }`
   - `unordered_map<int, Entry> entries`: maps `key` to its entry.
   - `unordered_map<int, list<int>> byCount`: maps `count` to a doubly linked list of keys (front is MRU, back is LRU).
   - `int minCount`: stores the current minimum frequency in the cache.
2. Helper `touch(key)`:
   - Fetch entry `e = entries[key]`.
   - Remove `key` from `byCount[e.count]` using iterator `e.pos`.
   - If `byCount[e.count]` becomes empty:
     - Remove the empty frequency list from `byCount`.
     - If `minCount == e.count`, increment `minCount++`.
   - Increment `e.count++`.
   - Push `key` to the front of `byCount[e.count]` and update `e.pos`.
3. Operation `get(key)`:
   - If `key` not in `entries`, return -1.
   - Call `touch(key)` and return `entries[key].value`.
4. Operation `put(key, value)`:
   - If `cap == 0`, return immediately.
   - If `key` exists in `entries`:
     - Update `entries[key].value = value`.
     - Call `touch(key)` and return.
   - If `entries.size() == cap`:
     - Get list `victims = byCount[minCount]`.
     - Evict key `victims.back()`, erasing from `entries` and popping from `victims`.
     - If `victims` is empty, erase `minCount` from `byCount`.
   - Insert new key: push to front of `byCount[1]`.
   - Store `entries[key] = {value, 1, byCount[1].begin()}`.
   - Set `minCount = 1`.

Complexity:
- Time: $O(1)$ average time per `get` and `put` call. All operations involve hash map lookups and $O(1)$ doubly linked list splicing/removal.
- Space: $O(\text{capacity})$ auxiliary space to store entries, frequency lists, and iterators for at most `capacity` items.

## Code walkthrough

In the reference implementation:
- `old.erase(e.pos);`: unlinks the key from its current frequency list in $O(1)$ without scanning.
- `if (old.empty() && minCount == e.count) minCount++;`: updates the global minimum frequency pointer when the previous minimum bucket empties.
- `list<int>& victims = byCount[minCount]; entries.erase(victims.back());`: identifies and purges the least frequently and least recently used entry in $O(1)$.
- `minCount = 1;`: correctly resets minimum frequency upon adding a new key.

## Test it out loud

- Capacity 0: `LFUCache(0)`. `put(0, 0)` does nothing; `get(0)` returns -1.
- Frequency elevation: `capacity = 2`. `put(1, 1)`, `put(2, 2)`. Both at count 1. `get(1)` moves 1 to count 2, `minCount` remains 1 (since 2 is still at count 1). `put(3, 3)` evicts 2 (count 1), sets `minCount = 1` for 3.
- Equal frequency eviction order: Two keys with count 2; eviction pops from the back of the count-2 doubly linked list, removing the one accessed longest ago.

## Follow-ups

- How to implement this in Python without manual pointers?
  Use `collections.OrderedDict` as the bucket inside `defaultdict(OrderedDict)`. Its `popitem(last=False)` pops the oldest item in $O(1)$.
- What is the difference between LRU and LFU in real-world caching?
  LFU resists pollution from short bursts of single-access scans (which pollute LRU), but suffers from "cache starvation" where stale historical hot keys stay cached forever unless frequency aging / decay is implemented.
- How to implement frequency decay?
  Periodically halve all frequency counts or shift them downward after a fixed epoch window.

## Common mistakes

- Forgetting to handle `capacity == 0` as a special case, which causes crash on eviction.
- Failing to increment `minCount` when the last key with frequency `minCount` has its count incremented.
- Not resetting `minCount = 1` when a brand new key is inserted.
