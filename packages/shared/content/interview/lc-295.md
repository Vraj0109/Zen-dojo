## Clarify first

- What operations must be supported? (`addNum(num)` to insert a number from a stream, and `findMedian()` returning the current median as a double).
- What defines the median? (If the count of numbers $n$ is odd, the exact middle element; if $n$ is even, the arithmetic mean of the two middle elements).
- Can numbers be negative? (Yes, $-100,000 \le num \le 100,000$).
- Can `findMedian` be called before any numbers are added? (The problem guarantees at least one `addNum` has occurred prior to `findMedian`).
- What are the call volume limits? (Up to 100,000 total calls).

## Examples to say out loud

- Stream progression:
  - `addNum(1)`
  - `addNum(2)`
  - `findMedian()` $\implies (1 + 2) / 2 = 1.5$
  - `addNum(3)` $\implies$ sorted stream is `[1, 2, 3]`. Count is odd.
  - `findMedian()` $\implies$ middle element is 2.
- Stream with negative numbers:
  - `addNum(-1)`, `addNum(-2)` $\implies$ median is $-1.5$.
  - `addNum(-3)` $\implies$ median is $-2$.

## Brute force

A naive approach appends each incoming number to a dynamic array. Whenever `findMedian()` is called, sort the entire array in $O(n \log n)$ time and pick the middle element(s). For $10^5$ operations, repeated sorting takes $O(n^2 \log n) \approx 10^{11}$ operations, resulting in Time Limit Exceeded.
Alternatively, maintaining a sorted array with insertion sort takes $O(n)$ time per `addNum` due to element shifting, resulting in $O(n^2)$ overall time.

## The key observation

We only care about the element(s) in the immediate middle of the sorted order; we do not need the full dataset to be completely sorted.
Split the numbers into two halves:
1. `lo`: a **max-heap** storing the smaller half of numbers (the largest of the smaller half sits on top).
2. `hi`: a **min-heap** storing the larger half of numbers (the smallest of the larger half sits on top).
Maintain two invariants:
- Every element in `lo` is $\le$ every element in `hi` (`lo.top() <= hi.top()`).
- Sizes are balanced such that `lo.size() == hi.size()` (when total count is even) or `lo.size() == hi.size() + 1` (when total count is odd).
With these invariants, the median is immediately accessible in $O(1)$: if odd, `lo.top()`; if even, `(lo.top() + hi.top()) / 2.0`.

## Optimal approach

1. Maintain two priority queues:
   - `priority_queue<int> lo`: max-heap for lower half.
   - `priority_queue<int, vector<int>, greater<int>> hi`: min-heap for upper half.
2. Operation `addNum(num)`:
   - Push `num` into `lo`.
   - Take the largest element from `lo` (`lo.top()`) and transfer it to `hi`. This guarantees `lo.top() <= hi.top()`.
   - Rebalance sizes: if `hi.size() > lo.size()`, pop `hi.top()` and push it back to `lo`.
   - After this step, `lo` has either equal size to `hi` or exactly 1 more element.
3. Operation `findMedian()`:
   - If `lo.size() > hi.size()`, return `lo.top()`.
   - Else, return `((double)lo.top() + hi.top()) / 2.0`.

Complexity:
- Time: `addNum` takes $O(\log n)$ time to push and pop from heaps of size $n/2$. `findMedian` takes $O(1)$ time by reading heap tops.
- Space: $O(n)$ total space to store the $n$ streamed numbers across both heaps.

## Code walkthrough

In the reference implementation:
- `lo.push(num); hi.push(lo.top()); lo.pop();`: filters the new number through `lo` into `hi`, maintaining the invariant that all numbers in `hi` are $\ge$ all numbers in `lo`.
- `if (hi.size() > lo.size()) { lo.push(hi.top()); hi.pop(); }`: enforces that `lo` holds the surplus element when $n$ is odd.
- `if (lo.size() > hi.size()) return lo.top();`: reads median in $O(1)$ directly from the top of the max-heap.
- `return ((double)lo.top() + hi.top()) / 2.0;`: handles the even case with floating point precision.

## Test it out loud

- Single number: `addNum(5)`. `lo` gets 5, moves to `hi`, `hi` is larger so 5 moves back to `lo`. `findMedian()` returns `lo.top() = 5`.
- Identical numbers: `addNum(4)` four times. Two 4s reside in `lo`, two 4s reside in `hi`. Median is $(4 + 4) / 2 = 4$.
- Out of order stream: Insert 1, 100, 2, 99, 3. Heaps automatically self-balance at each step, yielding accurate medians (1, 50.5, 2, 50.5, 3).

## Follow-ups

- What if all integer numbers in the stream are between 0 and 100?
  Use a frequency bucket array of size 101. `addNum` is $O(1)$, and `findMedian` scans the 101 buckets in $O(1)$ time to count up to $n/2$.
- What if 99% of all integer numbers are in range $[0, 100]$ and 1% are outliers?
  Keep a fixed frequency array for $[0, 100]$ and two small heaps/lists for numbers $< 0$ and $> 100$.
- How to support removing numbers from the stream?
  Use heaps with lazy deletion (hash map of pending deletions) as in Sliding Window Median.

## Common mistakes

- Performing integer division `(lo.top() + hi.top()) / 2` instead of floating point division `/ 2.0`, truncating fractional medians like `1.5` to `1`.
- Inserting into `lo` or `hi` directly based on a manual comparison without rebalancing, which can violate the order invariant.
- Re-sorting the array on each query, resulting in $O(n \log n)$ time per query.
