## Clarify first

- Are the intervals inclusive or half-open? (Half-open intervals `[startTime, endTime)`: starting at `startTime` up to but not including `endTime`).
- Does touching intervals count as an overlap? (No, a booking ending at 20 does not overlap a booking starting at 20).
- What should be returned if an overlap occurs? (Return `false` and do NOT store the booking).
- What is the range of timestamps? ($0 \le startTime < endTime \le 10^9$).
- How many `book` calls are made? (Up to 100,000 calls).

## Examples to say out loud

- Non-overlapping vs overlapping:
  - `book(10, 20)` $\implies$ returns `true` (calendar accepts `[10, 20)`).
  - `book(15, 25)` $\implies$ overlaps `[10, 20)` on `[15, 20)`, returns `false`.
  - `book(20, 30)` $\implies$ touches at 20, no overlap; returns `true`.
- Touching back-to-back:
  - `book(5, 10)`, `book(0, 5)`, `book(10, 15)`. All three are accepted with boundaries touching at 5 and 10.

## Brute force

A naive brute-force maintains a list of all accepted intervals `[s_i, e_i]`. On each call to `book(start, end)`, iterate through all existing $n$ bookings and test the overlap condition: $\max(start, s_i) < \min(end, e_i)$. If an overlap is found, reject the booking; otherwise append it to the list. While easy to write, each call takes $O(n)$ time, leading to $O(n^2)$ total time across $10^5$ operations ($\approx 10^{10}$ operations), causing Time Limit Exceeded.

## The key observation

Because accepted intervals never overlap, they can be maintained in sorted order by start time in an **ordered map** (`std::map` in C++, `TreeMap` in Java).
For a candidate booking `[start, end)`:
- We do not need to check all bookings; only its **immediate predecessor** and **immediate successor** can possibly overlap it.
- Using binary search / `lower_bound(start)`, find the first booking starting at or after `start`:
  1. Successor check: If `next != end` and `next->start < end`, it overlaps with the next booking.
  2. Predecessor check: If a predecessor exists and `prev->end > start`, it overlaps with the preceding booking.
- If both checks pass, no other booking in the calendar can overlap it. Insert in $O(\log n)$ time.

## Optimal approach

1. Maintain an ordered map `booked`: mapping `start_time -> end_time`.
2. Operation `book(startTime, endTime)`:
   - Find iterator `next = booked.lower_bound(startTime)`.
   - If `next != booked.end()` and `next->first < endTime`:
     - The next event starts before our new event finishes; return `false`.
   - If `next != booked.begin()`:
     - Check predecessor `prev = std::prev(next)`.
     - If `prev->second > startTime`:
       - The preceding event ends after our new event starts; return `false`.
   - If neither overlaps, insert `booked[startTime] = endTime`.
   - Return `true`.

Complexity:
- Time: $O(\log n)$ time per `book` call, where $n$ is the number of currently accepted bookings. Red-black tree search (`lower_bound`) and insertion take logarithmic time.
- Space: $O(n)$ auxiliary space to store $n$ non-overlapping intervals in the ordered map.

## Code walkthrough

In the reference implementation:
- `map<int, int> booked;`: self-balancing binary search tree holding intervals sorted by start time.
- `auto next = booked.lower_bound(startTime);`: locates the earliest booking starting at or after `startTime` in $O(\log n)$.
- `if (next != booked.end() && next->first < endTime) return false;`: checks collision with the successor.
- `if (next != booked.begin() && prev(next)->second > startTime) return false;`: checks collision with the predecessor.
- `booked[startTime] = endTime; return true;`: commits the valid booking.

## Test it out loud

- Enclosed overlap: `book(10, 20)` accepted. `book(12, 14)` queries `lower_bound(12)` $\implies [10, 20)$. Predecessor ends at 20 ($20 > 12$), returns `false`.
- Touching boundaries: `book(10, 20)` and candidate `book(20, 25)`. `next` is end; `prev` ends at 20. Condition `20 > 20` is false. Accepted, returns `true`.
- Reverse chronological insertion: Bookings arrive in decreasing order: `book(20, 30)`, then `book(10, 20)`, then `book(0, 10)`. Each inserts before the head in $O(\log n)$ without overlap.

## Follow-ups

- What if double bookings are allowed (My Calendar II)?
  Maintain two lists: single bookings and overlapping double bookings; verify candidate does not overlap any interval in the double bookings list.
- What if $k$-bookings are allowed (My Calendar III)?
  Use a difference map / sweep-line: increment count at `startTime`, decrement at `endTime`, and compute prefix max.
- Can this be solved with a Segment Tree?
  Yes, a dynamic (sparse) segment tree over coordinates $[0, 10^9]$ supports range queries and updates in $O(\log(\text{max\_time}))$, which is suitable when intervals can be queried without explicit interval objects.

## Common mistakes

- Treating `endTime` as inclusive: using `<=` instead of `<` in `next->first < endTime`, incorrectly refusing bookings that only touch endpoints.
- Forgetting to check `next != booked.begin()` before decrementing `next`, causing an invalid iterator dereference on the first element.
- Attempting to use an unordered hash map, which cannot perform predecessor/successor range queries.
