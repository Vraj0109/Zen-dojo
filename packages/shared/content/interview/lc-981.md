## Clarify first

- Are timestamps strictly increasing for a given key? (Yes, the problem guarantees that for any specific key, timestamps passed to `set` arrive in strictly increasing order).
- What should `get(key, timestamp)` return if no value exists at or before `timestamp`? (Return an empty string `""`).
- If an exact timestamp match exists, does it return that value? (Yes, it returns the value at the latest time $\le timestamp$).
- Can different keys have interleaved timestamps? (Yes, but within any single key, timestamps are strictly increasing).
- How many operations are expected? (Up to 200,000 total calls to `set` and `get`).

## Examples to say out loud

- Historical lookup:
  - `set("foo", "bar", 1)`
  - `get("foo", 1)` $\implies$ `"bar"`
  - `get("foo", 3)` $\implies$ `"bar"` (latest value $\le 3$ is at timestamp 1)
  - `set("foo", "bar2", 4)`
  - `get("foo", 4)` $\implies$ `"bar2"`
  - `get("foo", 5)` $\implies$ `"bar2"`
- Query before any entry:
  - `set("a", "x", 5)`
  - `get("a", 4)` $\implies$ `""` (no entry exists at or before time 4)

## Brute force

A naive implementation stores all records in a single unsorted list of tuples `(key, value, timestamp)`. On `get(key, timestamp)`, scan the entire list to find all entries matching `key` with timestamp $\le query\_timestamp$, and take the one with the maximum timestamp. This takes $O(1)$ for `set`, but $O(M)$ for every `get` call where $M$ is the total number of operations. Across $2 \cdot 10^5$ operations, this results in $O(M^2) \approx 4 \times 10^{10}$ operations and Time Limit Exceeded.

## The key observation

Because timestamps for any given key arrive in strictly increasing order, appending new `(timestamp, value)` pairs to a vector automatically keeps that vector sorted by time.
- A hash map `key -> vector<pair<int, string>>` groups entries by key in $O(1)$ average time.
- To answer `get(key, timestamp)`, we locate the key's vector in $O(1)$ and then perform a binary search (`upper_bound` or `bisect_right`) to find the largest timestamp $\le query\_timestamp$ in $O(\log N)$ time.

## Optimal approach

1. Maintain an internal hash table `data`:
   - `unordered_map<string, vector<pair<int, string>>> data`
2. Operation `set(key, value, timestamp)`:
   - Append `{timestamp, value}` to `data[key]`. Since timestamps for each key are strictly increasing, `data[key]` remains naturally sorted.
3. Operation `get(key, timestamp)`:
   - Look up `key` in `data`. If not found, return `""`.
   - Let `v = data[key]`. Perform binary search over `v` using timestamps:
     - Find the first index `lo` where `v[lo].timestamp > timestamp`.
     - If `lo == 0`, every recorded timestamp is strictly greater than `timestamp`; return `""`.
     - Otherwise, the latest valid entry is at index `lo - 1`; return `v[lo - 1].value`.

Complexity:
- Time: `set` takes $O(1)$ amortized time per call. `get` takes $O(\log N)$ time per call where $N$ is the number of values stored for that specific key.
- Space: $O(N)$ total space where $N$ is the total number of key-value-timestamp entries stored.

## Code walkthrough

In the reference implementation:
- `data[key].push_back({timestamp, value});`: appends to the key's history in $O(1)$ while preserving sorted order.
- `int lo = 0, hi = v.size();`: binary search interval across the vector of entries.
- `if (v[mid].first <= timestamp) lo = mid + 1; else hi = mid;`: upper-bound binary search locates the first entry strictly exceeding `timestamp`.
- `return lo == 0 ? "" : v[lo - 1].second;`: checks if any valid historical record existed at or before the query time.

## Test it out loud

- Querying non-existent key: `get("c", 3)` on empty store. Key not found in hash map; returns `""`.
- Exact timestamp match: `set("love", "high", 10)`, `get("love", 10)`. Binary search finds `lo = 1`, returns `v[0].value = "high"`.
- Boundary timestamps: Key has entries at 100, 200, 300. Query at 99 returns `""`; query at 250 returns `"v2"`; query at 1000 returns `"v3"`.

## Follow-ups

- What if timestamps for a given key do not arrive in increasing order?
  Instead of appending to a vector, store pairs in a balanced binary search tree (`std::map<int, string>`), which maintains sorted order with $O(\log N)$ inserts and `upper_bound` queries in $O(\log N)$.
- What if keys require a maximum expiration time (TTL)?
  Store TTL along with value; during `get`, verify whether `query_timestamp - entry.timestamp <= TTL`.
- How to make this thread-safe?
  Use a concurrent hash map or protect each key's vector with a per-key mutex / read-write lock (`shared_mutex`).

## Common mistakes

- Using a single global list or tree, forcing all keys to compete in the same binary search structure.
- Returning an exact match only, rather than the latest timestamp $\le query\_timestamp$.
- Off-by-one errors in binary search: confusing `lower_bound` with `upper_bound`, failing to handle when the query timestamp matches an entry exactly.
