## Clarify first
- What defines a peak element? An element that is strictly greater than its neighbors. Positions before index 0 and after index n - 1 are treated as negative infinity.
- Are adjacent elements guaranteed to be different? Yes, `nums[i] != nums[i + 1]` for all valid i.
- Is the peak unique? While the original problem accepts any peak, the constraints here specify that exactly one peak exists in the array.
- What should be returned if n is 1? Index 0 is strictly greater than negative infinity on both sides, so 0 is returned.

## Examples to say out loud
- Consider `nums = [1, 2, 3, 1]`.
  - At index 2, element 3 has neighbors 2 and 1. Since 3 > 2 and 3 > 1, index 2 is a peak.
- Monotonically increasing case: `nums = [1, 2, 3, 4, 5]`.
  - At index 4, element 5 is greater than 4 and greater than out-of-bounds negative infinity, so index 4 is the peak.
- Monotonically decreasing case: `nums = [5, 4, 3, 2, 1]`.
  - At index 0, element 5 is greater than negative infinity and greater than 4, so index 0 is the peak.

## Brute force
A linear scan inspects every element from index 0 to n - 1 and checks whether it is strictly greater than both its left and right neighbors. This takes O(n) time and O(1) space. However, because the problem asks for logarithmic runtime, we can exploit the slope between adjacent elements using binary search.

## The key observation
Compare `nums[mid]` with `nums[mid + 1]`. Since adjacent elements are never equal:
- If `nums[mid] < nums[mid + 1]`, the array is currently ascending at `mid`. Because values must eventually stop climbing before or at the right boundary (as boundary values descend to negative infinity), there must be a peak to the right of `mid`. We can eliminate the range `[lo, mid]`.
- If `nums[mid] > nums[mid + 1]`, the array is descending from `mid`. This means either `mid` itself is a peak, or a peak lies strictly to its left. We can eliminate the range `[mid + 1, hi]`.
This guarantees halving the search space each step.

## Optimal approach
1. Initialize `lo = 0` and `hi = n - 1`.
2. While `lo < hi`:
   - Compute `mid = lo + (hi - lo) / 2`.
   - If `nums[mid] < nums[mid + 1]`: the sequence is increasing; set `lo = mid + 1`.
   - Else: the sequence is decreasing; set `hi = mid`.
3. When `lo == hi`, the search interval has converged to a single element. Return `lo`.

Complexity:
- Time complexity: O(log n) because each iteration discards half the search range.
- Space complexity: O(1) auxiliary space as only a few pointers are used.

## Code walkthrough
- `int lo = 0, hi = (int)nums.size() - 1`: Covers the entire array indices.
- `int mid = lo + (hi - lo) / 2`: Prevents integer overflow.
- `if (nums[mid] < nums[mid + 1]) lo = mid + 1`: Follows the upward slope toward the peak.
- `else hi = mid`: Shrinks the window while keeping the candidate peak `mid` within the active search space.
- Returns `lo`.

## Test it out loud
- Test `nums = [1, 2, 3, 1]`:
  - `lo = 0, hi = 3`, `mid = 1`. `nums[1] (2) < nums[2] (3)`. Set `lo = 2`.
  - `lo = 2, hi = 3`, `mid = 2`. `nums[2] (3) > nums[3] (1)`. Set `hi = 2`.
  - `lo == hi == 2`. Return 2.
- Test `nums = [5]`:
  - `lo = 0, hi = 0`. Loop doesn't execute; returns 0 immediately.

## Follow-ups
- What if duplicates were allowed (`nums[i] == nums[i + 1]`)? Binary search would degrade to O(n) in the worst case (like an array of identical elements) because slope direction could not be determined.
- Can this approach be adapted to 2D matrices? Yes, finding a peak in a 2D matrix can be achieved in O(r log c) by binary searching columns and finding the column maximum.

## Common mistakes
- Comparing `nums[mid]` against both `nums[mid - 1]` and `nums[mid + 1]`, which introduces boundary index checks when `mid == 0` or `mid == n - 1`.
- Using `hi = mid - 1` when `nums[mid] > nums[mid + 1]`, which accidentally discards `mid` when `mid` itself is the peak.
