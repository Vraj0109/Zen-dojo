## Clarify first

- What defines an overlap? Two intervals overlap if they share more than a single endpoint; intervals that merely touch, like `[1, 2]` and `[2, 3]`, do not overlap.
- What is the objective? Return the minimum number of intervals to delete so that all remaining intervals are mutually non-overlapping.
- Are the input intervals guaranteed to be sorted? No, intervals can arrive in any arbitrary order.
- What are the constraints on array length? Length is between 1 and 100,000, with coordinates between -50,000 and 50,000.

## Examples to say out loud

- Classic chain with conflict: `intervals = [[1, 2], [2, 3], [3, 4], [1, 3]]`.
  - Removing `[1, 3]` leaves `[1, 2]`, `[2, 3]`, and `[3, 4]`, which do not overlap. Minimum removals = 1.
- Identical duplicates: `intervals = [[1, 2], [1, 2], [1, 2]]`.
  - Must remove 2 intervals so only one `[1, 2]` remains. Minimum removals = 2.
- Naturally disjoint intervals: `intervals = [[1, 2], [2, 3]]`. No overlap, minimum removals = 0.

## Brute force

A brute-force strategy considers all possible subsets of intervals (up to `2^n`), checks if each subset has no overlapping pairs, and finds the largest non-overlapping subset of size `k`. The answer is then `n - k`. For `n = 100,000`, generating `2^{100,000}` subsets is completely impossible.

## The key observation

Minimizing the number of removed intervals is mathematically equivalent to **maximizing the number of compatible non-overlapping intervals kept** (the classic Activity Selection Problem). A greedy policy that repeatedly selects the compatible interval that finishes earliest (smallest `end` time) is provably optimal. Why? An interval that finishes earlier leaves the maximum possible remaining room for future intervals to be scheduled without conflict.

## Optimal approach

1. Sort the list of intervals ascending by their end time: `intervals[i][1]`.
2. Initialize `removed = 0` and `end = -infinity` (representing the end coordinate of the last retained interval).
3. For each interval `iv` in the sorted list:
   a. If `iv[0] >= end`:
      - The interval does not conflict with the last retained interval.
      - Keep this interval and update `end = iv[1]`.
   b. Otherwise:
      - The interval conflicts with the current schedule.
      - Discard this interval and increment `removed++`.
4. Return `removed`.

Complexity:
- Time: `O(n log n)` due to sorting `n` intervals by their end time, followed by an `O(n)` linear sweep.
- Space: `O(1)` auxiliary space beyond the sorting buffer.

## Code walkthrough

In the reference implementation:
- `sort(intervals.begin(), intervals.end(), [](auto& a, auto& b) { return a[1] < b[1]; });`: orders intervals by finish time.
- `int removed = 0, end = INT_MIN;`: initializes removal counter and baseline end marker.
- `for (auto& iv : intervals)`: sequentially evaluates intervals in order of earliest finish.
- `if (iv[0] >= end) end = iv[1];`: accepts non-overlapping interval and advances the active finish line.
- `else removed++;`: counts discarded overlapping interval.
- `return removed;`: outputs total intervals eliminated.

## Test it out loud

- `intervals = [[1, 2], [2, 3], [3, 4], [1, 3]]`:
  - Sorted by end: `[1, 2]`, `[2, 3]`, `[1, 3]`, `[3, 4]`.
  - `iv = [1, 2]`: `1 >= INT_MIN`, keep it. `end = 2`.
  - `iv = [2, 3]`: `2 >= 2`, keep it. `end = 3`.
  - `iv = [1, 3]`: `1 < 3`, conflict! Discard: `removed = 1`.
  - `iv = [3, 4]`: `3 >= 3`, keep it. `end = 4`.
  - Result: `removed = 1`.
- `intervals = [[1, 2], [1, 2]]`:
  - Keep first `[1, 2]`, `end = 2`. Second `1 < 2` discarded: `removed = 1`.

## Follow-ups

- What if we sorted by start time instead of end time?
  Sorting by start time requires dynamically tracking and shrinking `end = min(end, iv[1])` whenever an overlap occurs; sorting by end time is simpler and cleaner.
- How does this problem relate to Minimum Number of Arrows to Burst Balloons (LeetCode 452)?
  LeetCode 452 finds the minimum points to intersect all intervals, which equals the number of non-overlapping intervals found via the same greedy earliest-finish schedule.

## Common mistakes

- Sorting by start time without handling the case where a long interval swallows a shorter one, causing incorrect greedy selections.
- Counting touching endpoints as overlapping (e.g. treating `[1, 2]` and `[2, 3]` as conflicting when `2 >= 2` is valid).
- Using dynamic programming `O(n^2)` (similar to LIS) when greedy activity selection runs in `O(n log n)`.
