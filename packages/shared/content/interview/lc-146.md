## Clarify first

- What operations must be supported? (`get(key)` returning value or -1, and `put(key, value)` inserting or updating).
- What defines "least recently used"? (Both `get` and `put` count as using a key; eviction targets the key accessed longest ago).
- What is the cache capacity? ($1 \le capacity \le 3000$).
- What should happen if `put` updates an existing key when capacity is full? (The value is updated and marked most recent, but no eviction occurs since cache size does not increase).
- What are the time complexity requirements? (Both `get` and `put` must run in strict $O(1)$ average time).

## Examples to say out loud

- Eviction order: `capacity = 2`.
  - `put(1, 1)`, `put(2, 2)`: Cache holds `[2, 1]` (2 is most recent).
  - `get(1)`: Returns 1, moves 1 to most recent $\implies [1, 2]$.
  - `put(3, 3)`: Cache exceeds capacity; evicts least recently used (2). Cache now holds `[3, 1]`.
  - `get(2)`: Key 2 was evicted; returns -1.
- Update existing key: `put(1, 10)` on existing key 1 updates value to 10 and moves 1 to front without evicting anything.

## Brute force

A naive approach uses an array or list of pairs `(key, value)` with timestamps. On each `get(key)`, iterate through the list to find the key and update its timestamp in $O(n)$ time. On each `put`, scan the list to update an existing key, or scan to find the minimum timestamp when at capacity, which takes $O(n)$ time. With up to $2 \cdot 10^5$ operations, $O(n)$ per call results in $O(n \cdot q) \approx 6 \times 10^8$ operations, failing the $O(1)$ requirement.

## The key observation

To achieve $O(1)$ time for both lookups and recency reordering:
1. A **hash map** provides $O(1)$ key-to-node lookup.
2. A **doubly linked list** allows $O(1)$ node insertion, removal, and movement to the front (most recent) or back (least recent), provided we already have a pointer to the node.
By combining a hash map pointing to doubly linked list nodes (or using `std::list::iterator` in C++), accessing a node via the map allows us to splice/unlink it and move it to the head in $O(1)$, while eviction simply drops the node preceding the dummy tail.

## Optimal approach

1. Maintain:
   - An integer `cap` for maximum capacity.
   - A doubly linked list of pairs `(key, value)` ordered from most recently used (head) to least recently used (tail).
   - A hash map `where` mapping each `key` to its corresponding iterator/node in the list.
2. Operation `get(key)`:
   - Look up `key` in `where`. If absent, return -1.
   - Node exists: move it to the front of the list (mark most recently used).
   - Return the node's value.
3. Operation `put(key, value)`:
   - Look up `key` in `where`.
   - If present: update its value, move the node to the front of the list, and return.
   - If absent:
     - If the list size equals `cap`:
       - Evict the least recently used element at the back (`items.back()`).
       - Erase its key from the hash map `where`.
       - Pop the node from the back of the list.
     - Insert a new `(key, value)` node at the front of the list.
     - Record `where[key] = items.begin()`.

Complexity:
- Time: $O(1)$ average time per `get` and `put` call. Hash map operations take $O(1)$ average time, and doubly linked list pointer updates take strictly $O(1)$.
- Space: $O(\text{capacity})$ auxiliary space to store at most `capacity` nodes and hash map entries.

## Code walkthrough

In the reference implementation:
- `list<pair<int, int>> items;`: maintains access ordering from front (MRU) to back (LRU).
- `unordered_map<int, list<pair<int, int>>::iterator> where;`: provides $O(1)$ iterator access given a key.
- `items.splice(items.begin(), items, it->second);`: unlinks and splices the existing node to the front in $O(1)$ without memory reallocation.
- `where.erase(items.back().first); items.pop_back();`: purges the victim key and node when capacity is exceeded.
- `items.emplace_front(key, value); where[key] = items.begin();`: inserts the new entry as the most recently used.

## Test it out loud

- Capacity 1: `LRUCache(1)`. `put(2, 1)`, `get(2)` returns 1. `put(3, 2)` evicts 2, cache has `[3]`. `get(2)` returns -1, `get(3)` returns 2.
- Multiple gets without puts: Repeated `get` calls on the same key keep it at the front, preserving correct eviction order for untouched keys.
- Update value without capacity increase: `capacity = 2`. `put(1, 1)`, `put(2, 2)`, `put(1, 10)`. Node 1 is updated to 10 and moved to front. Next `put(3, 3)` evicts 2 (not 1).

## Follow-ups

- How to make this thread-safe in a concurrent environment?
  Use a read-write lock (`std::shared_mutex`) or fine-grained sharding (Striped LRU Cache) where keys are hashed across multiple smaller LRU buckets to reduce lock contention.
- What if keys expire after a Time-To-Live (TTL)?
  Store an expiration timestamp with each node, and maintain a min-heap or secondary time-ordered queue to lazily or proactively expire stale keys.
- How does Python's `collections.OrderedDict` implement this?
  It internally combines a hash table with a doubly linked list, providing `move_to_end()` and `popitem()` in $O(1)$ time.

## Common mistakes

- Storing only values in the doubly linked list nodes: the node must also store the `key` so that when the tail is evicted, we can find and delete the key from the hash map.
- Using a singly linked list: unlinking a node in a singly linked list requires $O(n)$ to find its predecessor.
- Forgetting that `put` of an existing key makes it the most recently used.
