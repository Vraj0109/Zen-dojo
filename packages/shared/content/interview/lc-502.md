## Clarify first
- Can we pick the same project more than once? No, at most k distinct projects can be chosen.
- Does starting a project consume our capital? No, the capital is a prerequisite threshold, not a cost; finishing a project strictly increases our capital by its profit.
- What if fewer than k projects are affordable? We do as many affordable projects as possible and terminate early if no more can be unlocked.
- Can initial capital `w` or accumulated money exceed 32-bit signed integer limits? Yes, cumulative capital can reach large values, so 64-bit integer tracking prevents overflow during accumulation.

## Examples to say out loud
- Consider `k = 2, w = 0`, with `profits = [1, 2, 3]` and `capital = [0, 1, 1]`.
  - Initially with capital 0, only project 0 (capital 0, profit 1) can be done.
  - After project 0, money becomes `0 + 1 = 1`.
  - Now projects 1 (profit 2) and 2 (profit 3) are both affordable. We pick the highest profit: project 2 with profit 3.
  - Final money: `1 + 3 = 4`.
- Edge case: `w = 0`, but all projects have `capital > 0`. We cannot start any project; final capital remains 0.

## Brute force
A brute force greedy approach searches through all remaining uncompleted projects in each of the k rounds, finds all projects with `capital[i] <= current_capital`, and picks the one with the maximum profit. For each of the k rounds, scanning up to n projects takes O(k * n) time. With n and k up to 100,000, O(k * n) requires 10^10 operations and times out.

## The key observation
Selecting the project with the highest profit among all currently affordable projects is always optimal. Because capital only increases upon completing projects, taking more profit earlier never restricts future choices; it strictly expands the set of affordable projects. We can sort all projects by required capital, then maintain a max-heap of profits for all projects whose capital requirement has been satisfied.

## Optimal approach
1. Pair each project's required capital and profit, and sort the pairs in ascending order of required capital.
2. Initialize a max-heap `pq` to store profits of currently affordable projects.
3. Keep an index pointer `idx = 0` to track the next project in the sorted capital list.
4. Repeat up to k rounds:
   - While `idx < n` and `proj[idx].capital <= money`: push `proj[idx].profit` into `pq` and increment `idx`.
   - If `pq` is empty: no more projects can be afforded, break out of the loop early.
   - Pop the maximum profit from `pq` and add it to `money`.
5. Return the final accumulated `money` capped at standard integer limits.

Complexity:
- Time complexity: O(n log n + k log n) where sorting projects by capital takes O(n log n), each project is pushed into and popped from the max-heap at most once across all rounds in O(n log n), and at most k extractions take O(k log n).
- Space complexity: O(n) to store the paired project list and the max-heap.

## Code walkthrough
- `vector<pair<int, int>> proj(n)` followed by `sort(proj.begin(), proj.end())`: Orders projects by required capital from least to greatest.
- `priority_queue<int> pq`: Standard C++ max-heap storing available profits.
- `while (idx < n && proj[idx].first <= money) pq.push(proj[idx++].second)`: Moves all newly affordable projects into the pool of candidates.
- `if (pq.empty()) break`: Handles situations where current capital cannot unlock any further projects.
- `money += pq.top(); pq.pop()`: Greedily consumes the project yielding the highest profit.

## Test it out loud
- Test `k = 1, w = 0, profits = [5], capital = [1]`:
  - `proj = [(1, 5)]`.
  - Round 1: `money = 0 < proj[0].capital (1)`, heap remains empty.
  - Break; return 0.
- Test `k = 3, w = 100, profits = [1, 2, 3], capital = [5, 5, 5]`:
  - All projects affordable immediately.
  - Heap gets `1, 2, 3`.
  - Pops 3, then 2, then 1, adding 6 total to give 106.

## Follow-ups
- What if projects actually consume capital when started? Then the problem transitions into a variant of the knapsack problem (0/1 Knapsack / dynamic programming) where greedy choice is no longer optimal.
- What if k >= n? We can simply push all projects into the heap as capital allows and take up to n highest available profits.

## Common mistakes
- Deducting capital upon starting a project instead of just verifying that current money meets the requirement.
- Re-scanning all projects from scratch on each round instead of advancing a single pointer along the sorted capital array.
- Missing the early exit when the priority queue is empty before completing k rounds.
