## Clarify first
- Is the subarray sum inclusive of both bounds `lower` and `upper`? Yes, `lower <= sum <= upper`.
- Can the elements and sums be negative? Yes, array elements can be negative, so prefix sums are not monotonic.
- Can individual elements or subarray sums overflow a 32-bit signed integer? Yes, elements range between `-2^31` and `2^31 - 1`, so 64-bit integers are required for prefix sums.
- What is the maximum length of `nums`? Up to `100000`.

## Examples to say out loud
- Consider `nums = [-2, 5, -1], lower = -2, upper = 2`:
  - Prefix sums `P = [0, -2, 3, 2]`.
  - Subarray `[0..0]` sum = -2 (in range).
  - Subarray `[2..2]` sum = -1 (in range).
  - Subarray `[0..2]` sum = 2 (in range).
  - Output is 3.
- Consider `nums = [0], lower = 0, upper = 0`:
  - Single element subarray `[0]` has sum 0, within `[0, 0]`.
  - Output is 1.

## Brute force
Computing all `O(n^2)` subarray sums using prefix sums and checking if `lower <= P[j] - P[i] <= upper` takes `O(n^2)` time. With `n = 100000`, `n^2 = 10^10` operations, resulting in Time Limit Exceeded. We need an `O(n log n)` approach.

## The key observation
For a prefix sum array `P`, a subarray `(i, j]` has sum `P[j] - P[i]`. The condition `lower <= P[j] - P[i] <= upper` is equivalent to finding pairs `(i, j)` with `i < j` such that `P[j] - upper <= P[i] <= P[j] - lower`. This resembles counting inversions. During merge sort on the prefix sums, when merging two sorted halves `[l, m)` and `[m, r)`, for each `j` in `[m, r)` the valid indices `i` in `[l, m)` form a contiguous range `[a, b)`. Because both halves are sorted, both pointers `a` and `b` only advance forward, allowing all valid pairs crossing the midpoint to be counted in `O(r - l)` linear time.

## Optimal approach
1. Compute prefix sums array `P` of length `n + 1` with `P[0] = 0` using 64-bit integers.
2. Implement a divide-and-conquer function `sortCount(P, tmp, l, r)`:
   - If `r - l <= 1`, return 0.
   - Let `m = (l + r) / 2`.
   - Recursively count inside left and right halves: `res = sortCount(P, tmp, l, m) + sortCount(P, tmp, m, r)`.
   - Initialize two sliding pointers `a = l` and `b = l`.
   - For each right index `j` from `m` to `r - 1`:
     - Advance `a` while `a < m` and `P[j] - P[a] > upper`.
     - Advance `b` while `b < m` and `P[j] - P[b] >= lower`.
     - Add `b - a` to `res`.
   - Merge sorted sub-arrays `P[l..m)` and `P[m..r)` into `tmp[l..r)` and copy back to `P`.
   - Return `res`.
3. Return `sortCount(P, tmp, 0, n + 1)`.

Complexity:
- Time: `O(n log n)` time because the recurrence is `T(n) = 2T(n/2) + O(n)` like standard merge sort.
- Space: `O(n)` auxiliary space for prefix sums and temporary merge buffer.

## Code walkthrough
- `vector<long long> p(n + 1, 0);` stores cumulative sums with 64-bit precision.
- In `sortCount`:
  - `while (a < m && p[j] - p[a] > hi) a++;` advances `a` to the first index where `p[j] - p[a] <= hi`.
  - `while (b < m && p[j] - p[b] >= lo) b++;` advances `b` past the last index where `p[j] - p[b] >= lo`.
  - `res += b - a;` accumulates the count of valid prefix sum differences for current `j`.
  - Standard merge sort routine orders the values for parent recursive steps.

## Test it out loud
- Test single zero `nums = [0], lower = 0, upper = 0`: `P = [0, 0]`. Midpoint split counts pair `(0, 1)`, difference 0, returns 1.
- Test no matches `nums = [1, 2, 3], lower = 0, upper = 0`: All subarray sums are strictly positive, returns 0.
- Test all zeroes `nums = [0, 0, 0], lower = 0, upper = 0`: All `(4 * 3) / 2 = 6` pairs have difference 0, returns 6.
- Test negative elements `nums = [-1, -1, -1], lower = -2, upper = -1`: Finds 5 valid subarrays. Correct.

## Follow-ups
- Can this be solved using a Fenwick tree or Segment Tree?
  - Yes, coordinate compress all values `P[i]`, `P[i] - upper`, and `P[i] - lower`, insert prefix sums into a BIT, and query ranges `[P[j] - upper, P[j] - lower]` in `O(n log n)`.
- Why prefer merge sort over Fenwick tree in an interview?
  - Merge sort requires no coordinate compression and handles dynamic 64-bit ranges directly with minimal boilerplate.

## Common mistakes
- Using 32-bit integers for prefix sums, leading to overflow on accumulated sums.
- Forgetting to include index 0 (`P[0] = 0`) representing empty prefix, which misses valid subarrays starting at index 0.
- Advancing pointers incorrectly when `nums` contains duplicate or negative values.
