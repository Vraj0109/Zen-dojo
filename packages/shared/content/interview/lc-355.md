## Clarify first

- What operations must be supported? (`postTweet(userId, tweetId)`, `getNewsFeed(userId)`, `follow(followerId, followeeId)`, and `unfollow(followerId, followeeId)`).
- What appears in a user's news feed? (The 10 most recent tweet IDs posted by the user themselves or by anyone they follow, ordered newest first).
- Does a user always see their own tweets in their feed? (Yes, a user always sees their own tweets even without following themselves).
- Can a user follow themselves? (Constraints state `followerId != followeeId`).
- What if there are fewer than 10 tweets available? (Return all available tweets, sorted newest first).

## Examples to say out loud

- Follow, post, and unfollow flow:
  - User 1 posts tweet 5: `postTweet(1, 5)`. Feed for user 1: `[5]`.
  - User 1 follows user 2: `follow(1, 2)`.
  - User 2 posts tweet 6: `postTweet(2, 6)`.
  - Feed for user 1: `[6, 5]` (tweet 6 is newer than tweet 5).
  - User 1 unfollows user 2: `unfollow(1, 2)`.
  - Feed for user 1: `[5]` (user 2's tweets are immediately removed).

## Brute force

A naive fan-out-on-write approach maintains a precomputed feed list for each user. When `postTweet` is called, find all followers of `userId` and prepend `tweetId` to their feed lists. However, when `follow` or `unfollow` occurs, reconstructing the follower's entire feed history takes $O(T)$ time where $T$ is the total tweet count. Alternatively, pulling every tweet ever posted across all followed users and sorting all of them takes $O(T_{\text{total}} \log T_{\text{total}})$, which degrades as tweet counts grow.

## The key observation

Notice that a news feed only requires at most **10** most recent tweets in total.
Therefore, for any individual user or followee, **only their last 10 tweets can ever possibly appear in the final top-10 result**. Older tweets beyond their personal top-10 cannot make the cut.
- Use a global logical timestamp counter (`clock++`) to timestamp each tweet.
- When `getNewsFeed(userId)` is called, collect at most the last 10 tweets from `userId` and from each user in `follows[userId]`.
- If a user follows $F$ people, we gather at most $10 \times (F + 1)$ candidate tweets. Sorting these candidates (or merging them with a max-heap) takes $O(F \log F)$ time, independent of total historical tweet volume.

## Optimal approach

1. Maintain internal state:
   - `int clock = 0`: global monotonic timestamp generator.
   - `unordered_map<int, vector<pair<int, int>>> tweets`: maps `userId` to a list of `{time, tweetId}`.
   - `unordered_map<int, unordered_set<int>> follows`: maps `followerId` to the set of `followeeId`s.
2. Operation `postTweet(userId, tweetId)`:
   - Append `{clock++, tweetId}` to `tweets[userId]`.
3. Operation `follow(followerId, followeeId)`:
   - Insert `followeeId` into `follows[followerId]`.
4. Operation `unfollow(followerId, followeeId)`:
   - Erase `followeeId` from `follows[followerId]`.
5. Operation `getNewsFeed(userId)`:
   - Initialize `vector<pair<int, int>> pool`.
   - Helper `addLast10(u)`: if `u` has tweets, append the last $\min(10, \text{size})$ elements from `tweets[u]` into `pool`.
   - Call `addLast10(userId)` (user always sees their own tweets).
   - For each followee `f` in `follows[userId]`: call `addLast10(f)`.
   - Sort `pool` in descending order of timestamp.
   - Extract up to the first 10 `tweetId`s from `pool` and return them.

Complexity:
- Time: `postTweet`, `follow`, and `unfollow` run in $O(1)$ average time. `getNewsFeed` takes $O(F \log F)$ time where $F$ is the number of followees ($F \le 500$, so pool size $\le 5000$).
- Space: $O(U + T)$ auxiliary space where $U$ is the number of users and $T$ is the total number of tweets and follow relationships stored.

## Code walkthrough

In the reference implementation:
- `tweets[userId].push_back({clock++, tweetId});`: assigns an incremental logical timestamp to preserve global post ordering.
- `follows[followerId].insert(followeeId);`: set-based relationship mapping handles duplicate follow calls idempotently.
- `for (int i = max(0, (int)v.size() - 10); i < (int)v.size(); i++) pool.push_back(v[i]);`: bounds candidate pooling to at most 10 per author.
- `sort(pool.rbegin(), pool.rend());`: orders candidate tweets from most recent to oldest.
- `feed.push_back(pool[i].second);`: extracts the top 10 tweet IDs.

## Test it out loud

- User with >10 tweets: User 1 posts 12 tweets. `getNewsFeed(1)` returns tweets 12 down to 3 (exactly 10 tweets).
- User with 0 tweets: Returns empty list `[]`.
- Unfollowing non-followed user: Idempotent no-op via `follows[followerId].erase(followeeId)`.
- Concurrent followees: Multiple followees post interspersed tweets; timestamps ensure chronological ordering across authors.

## Follow-ups

- Can we optimize `getNewsFeed` using a k-way merge instead of sorting?
  Yes, each user's tweet list is already sorted by time. Using a max-heap of size $F + 1$, we can perform a k-way merge extracting the 10 largest elements in $O(F + 10 \log F)$ time.
- How does real Twitter architecture handle this?
  Celebrities with millions of followers use pull-on-read (fan-out on read) with caching, while standard users use push-on-write (fan-out on write) to precompute follower timelines.
- How to handle pagination?
  Accept an optional `cursor_time` or `max_tweet_id` parameter to fetch the next 10 tweets older than the cursor.

## Common mistakes

- Inserting all tweets of followed users into `pool` rather than only the last 10, leading to $O(T_{\text{total}} \log T_{\text{total}})$ performance degradation.
- Forgetting that a user must see their own tweets even if they follow no one.
- Not ensuring timestamps are strictly distinct across tweets (using wall-clock time with identical millisecond resolution instead of an atomic counter).
