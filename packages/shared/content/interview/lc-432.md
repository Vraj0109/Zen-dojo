## Clarify first

- What operations must be supported? (`inc(key)`, `dec(key)`, `getMaxKey()`, and `getMinKey()`).
- What should `getMaxKey()` and `getMinKey()` return if the structure is empty? (Return an empty string `""`).
- What happens when a key's frequency drops to 0 via `dec`? (The key is completely removed from the data structure).
- Is `dec` ever called on non-existent keys? (The problem guarantees `dec` is only called on keys that currently exist in the data structure).
- What is the time complexity requirement? (All operations must run in strict $O(1)$ average time).

## Examples to say out loud

- Basic tracking:
  - `inc("hello")`, `inc("hello")` $\implies$ `"hello"` has count 2. Both `getMaxKey()` and `getMinKey()` return `"hello"`.
  - `inc("leet")` $\implies$ `"leet"` has count 1. `getMaxKey()` returns `"hello"`, `getMinKey()` returns `"leet"`.
  - `dec("hello")` $\implies$ both `"hello"` and `"leet"` have count 1. Either is valid for min/max.
  - `dec("leet")` $\implies$ count of `"leet"` reaches 0 and is removed.

## Brute force

A naive approach uses an `unordered_map<string, int>` for frequencies. `inc` and `dec` run in $O(1)$ time. However, to answer `getMaxKey()` and `getMinKey()`, we must iterate through the entire hash map to find the minimum and maximum counts, taking $O(n)$ time per query where $n$ is the number of distinct keys. With $10^5$ operations, this takes $O(n \cdot q) \approx 10^{10}$ operations and results in Time Limit Exceeded.
Using a binary search tree or `std::map<int, set<string>>` as in some basic references takes $O(\log K)$ time (or $O(L \log N)$ with string set comparisons), which is suboptimal compared to the required $O(1)$.

## The key observation

To achieve true $O(1)$ time for every operation:
1. Maintain a **doubly linked list of buckets**, where each bucket represents a distinct frequency count and holds an `unordered_set<string>` of keys having that exact frequency.
2. The doubly linked list is maintained in strictly increasing order of frequency from head to tail.
3. A hash map `key -> list_iterator` points directly to the bucket node containing `key`.
4. When `inc(key)` is called, the key's frequency increases by exactly 1. Its new bucket must either already exist immediately to the right of its current bucket, or we can insert a new bucket node in $O(1)$ between current and next.
5. Symmetrically for `dec(key)`, the key moves to the predecessor bucket (frequency $- 1$). Empty buckets are unlinked in $O(1)$.
6. `getMaxKey()` and `getMinKey()` simply read an arbitrary element from the tail bucket and head bucket in $O(1)$!

## Optimal approach

1. Define structure `Bucket`:
   - `int count`
   - `unordered_set<string> keys`
2. Maintain:
   - A doubly linked list `list<Bucket> buckets` ordered by `count` ascending.
   - A hash map `unordered_map<string, list<Bucket>::iterator> keyToBucket`.
3. Operation `inc(key)`:
   - If `key` is not in `keyToBucket`:
     - If `buckets` is empty or `buckets.front().count != 1`, insert a new bucket `{1, {}}` at the front.
     - Add `key` to `buckets.front().keys` and record `keyToBucket[key] = buckets.begin()`.
   - Else:
     - Let `cur = keyToBucket[key]` and `nxt = next(cur)`.
     - If `nxt == buckets.end()` or `nxt->count != cur->count + 1`:
       - Insert a new bucket `{cur->count + 1, {}}` right after `cur`.
     - Move `key` from `cur->keys` to `next(cur)->keys`, updating `keyToBucket[key]`.
     - If `cur->keys.empty()`, erase `cur` from `buckets`.
4. Operation `dec(key)`:
   - Let `cur = keyToBucket[key]`.
   - If `cur->count == 1`:
     - Remove `key` from `cur->keys` and erase from `keyToBucket`.
   - Else:
     - Check if predecessor bucket `prv` has count `cur->count - 1`. If not, insert `{cur->count - 1, {}}` before `cur`.
     - Move `key` to `prv->keys`, updating `keyToBucket[key]`.
   - If `cur->keys.empty()`, erase `cur` from `buckets`.
5. Operation `getMaxKey()`:
   - Return `buckets.empty() ? "" : *buckets.back().keys.begin()`.
6. Operation `getMinKey()`:
   - Return `buckets.empty() ? "" : *buckets.front().keys.begin()`.

Complexity:
- Time: Strictly $O(1)$ average time per operation. Hash map lookups and unordered set insertions/deletions take $O(1)$ average, and doubly linked list node insertions and unlinking take $O(1)$ time.
- Space: $O(n)$ auxiliary space to store $n$ unique keys across buckets and map entries.

## Code walkthrough

In the optimal architecture:
- `list<Bucket> buckets;`: preserves sorted order of frequency buckets with $O(1)$ insertion of adjacent counts.
- `keyToBucket`: gives $O(1)$ direct access to the bucket containing the key.
- `buckets.insert(next(cur), {cur->count + 1, {}});`: dynamically splices a new bucket into the list in $O(1)$ when a frequency gap is created.
- `if (cur->keys.empty()) buckets.erase(cur);`: automatically garbage-collects empty frequency nodes.
- `*buckets.back().keys.begin()` / `*buckets.front().keys.begin()`: extracts any maximum/minimum key in $O(1)$.

## Test it out loud

- Empty data structure: `getMaxKey()` and `getMinKey()` return `""`.
- Increment and decrement to zero: `inc("z")` creates bucket 1, `dec("z")` removes from bucket 1, bucket empties and is erased. `getMaxKey()` returns `""`.
- Multiple keys with same frequency: `inc("a")`, `inc("b")`. Bucket 1 contains `{"a", "b"}`. `inc("a")` moves `"a"` to bucket 2. Bucket 1 holds `{"b"}`, bucket 2 holds `{"a"}`. Min returns `"b"`, max returns `"a"`.

## Follow-ups

- Why is a doubly linked list used instead of a balanced BST?
  Frequencies change by at most $\pm 1$ per operation. Because changes are strictly local to adjacent integers, a linked list allows $O(1)$ pointer adjustments, whereas a BST requires $O(\log K)$ rebalancing.
- How to return all keys with maximum frequency?
  Return the entire `keys` set of `buckets.back()` in $O(\text{size})$.
- What if keys can have arbitrary frequency increments (`incBy(key, delta)`)?
  If `delta > 1`, transitions are no longer adjacent, requiring a skip list or balanced search tree ($O(\log K)$).

## Common mistakes

- Using an ordered map `map<int, set<string>>`, which runs in $O(\log K)$ time rather than the required $O(1)$.
- Forgetting to erase empty bucket nodes from the doubly linked list, causing `getMaxKey()` or `getMinKey()` to read from empty buckets.
- Memory corruption when updating `keyToBucket` if the key is removed from the old bucket after modifying the iterator.
