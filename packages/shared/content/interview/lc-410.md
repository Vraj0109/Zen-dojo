## Clarify first

- Must the `k` parts be non-empty and contiguous? Yes, the split must divide `nums` into exactly `k` contiguous, non-empty subarrays.
- Can `nums[i]` be negative? No, constraints state elements are non-negative (`0 <= nums[i] <= 1,000,000`).
- What if `k == nums.length`? Each element forms its own part, so the answer is `max(nums)`.
- What if `k == 1`? The entire array forms a single part, so the answer is `sum(nums)`.
- What are the constraints on array length and values? `nums.length` is between 1 and 1,000, and `k <= min(50, nums.length)`.

## Examples to say out loud

- Standard partition: `nums = [7, 2, 5, 10, 8]`, `k = 2`.
  - Partitioning as `[7, 2, 5]` (sum = 14) and `[10, 8]` (sum = 18): max part sum is 18.
  - No split can achieve a smaller maximum part sum. Result is 18.
- Equal parts: `nums = [1, 2, 3, 4, 5]`, `k = 2`.
  - Best split is `[1, 2, 3]` (sum = 6) and `[4, 5]` (sum = 9): max sum is 9.
- Single part edge case: `nums = [1, 4, 4]`, `k = 3`. Max part sum is 4.

## Brute force

A brute-force dynamic programming approach defines `dp[i][j]` as the minimum largest subarray sum when splitting prefix `nums[0..i]` into `j` parts. To compute `dp[i][j]`, iterate over all possible partition split points `p < i`: `dp[i][j] = \min_{p} \max(dp[p][j - 1], \text{sum}(nums[p+1..i]))`. With `n = 1,000` and `k = 50`, this DP takes `O(k \times n^2)` time, requiring `5 \times 10^7` operations. While viable, binary search is much faster and simpler.

## The key observation

Instead of asking "where should the `k` split points be placed?", invert the question: "Can we partition the array into at most `k` parts such that **no part sum exceeds `X`**?"
This feasibility condition is monotonic: if a maximum part sum of `X` is achievable, any larger sum `X' > X` is also achievable. To test feasibility of `X`, greedily add numbers to the current part until adding the next number would exceed `X`, then start a new part. If the total parts used is `<= k`, `X` is feasible. We can binary search `X` between `max(nums)` and `sum(nums)`.

## Optimal approach

1. Set search range:
   - `lo = max(nums)` (a part cannot be smaller than the largest single element).
   - `hi = sum(nums)` (a part never needs to exceed the total array sum).
2. While `lo < hi`:
   a. Compute candidate limit `mid = lo + (hi - lo) / 2`.
   b. Test feasibility of limit `mid`:
      - Initialize `parts = 1` and `cur = 0`.
      - For each number `x` in `nums`:
        - If `cur + x > mid`:
          - Increment `parts++`.
          - Reset `cur = 0`.
        - Add `cur += x`.
   c. If `parts <= k`:
      - Feasible with at most `k` parts; try smaller: `hi = mid`.
   d. Otherwise:
      - Too many parts needed; limit is too tight: `lo = mid + 1`.
3. Return `(int)lo`.

Complexity:
- Time: `O(n log(sum))` where `n` is `nums.length` and `sum` is the total sum of elements. Each binary search check runs in `O(n)` time, taking at most 40 iterations.
- Space: `O(1)` auxiliary space as only scalar counters are maintained.

## Code walkthrough

In the reference implementation:
- `long long lo = *max_element(nums.begin(), nums.end()), hi = accumulate(nums.begin(), nums.end(), 0LL);`: establishes 64-bit boundaries for the search interval.
- `long long mid = (lo + hi) / 2, cur = 0; int parts = 1;`: prepares greedy partitioning for candidate threshold `mid`.
- `if (cur + x > mid) { parts++; cur = 0; } cur += x;`: packs elements into the current subarray until exceeding `mid`.
- `if (parts <= k) hi = mid; else lo = mid + 1;`: narrows the binary search toward the minimal valid threshold.
- `return (int)lo;`: returns the optimal minimized maximum sum.

## Test it out loud

- `nums = [7, 2, 5, 10, 8], k = 2`:
  - `lo = 10, hi = 32`.
  - At `mid = 18`:
    - `cur + 7 = 7`, `+ 2 = 9`, `+ 5 = 14`.
    - Next is 10: `14 + 10 = 24 > 18`, so new part! `parts = 2`, `cur = 10`.
    - `10 + 8 = 18 <= 18`.
    - Total `parts = 2 <= 2`. Feasible! `hi = 18`.
  - At `mid = 17`: requires 3 parts `([7, 2, 5], [10], [8])` > 2. Infeasible! `lo = 18`.
  - Converges to 18.

## Follow-ups

- What if `k` parts can be non-contiguous (subsets instead of subarrays)?
  That is the NP-hard multiprocessor scheduling / bin packing problem, requiring backtracking or branch-and-bound.
- How does this generalize to Painter's Partition Problem or Book Allocation Problem?
  They are the exact same problem: minimize the maximum work assigned to `k` workers.

## Common mistakes

- Initializing `lo = 0` instead of `max(nums)`, which allows candidate values of `mid` smaller than an individual element, causing `cur + x > mid` on an empty part.
- Starting `parts = 0` instead of `parts = 1`, resulting in an off-by-one undercount of partition segments.
- Using 32-bit signed integers for `hi` and `mid` when the total sum can exceed `2^{31} - 1`.
