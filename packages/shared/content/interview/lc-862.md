## Clarify first
- Can array elements be negative or zero? Yes, elements can be negative, which means prefix sums are non-monotonic.
- What should be returned if no contiguous subarray sums to at least k? Return -1.
- Can k be non-positive? No, k is at least 1.
- What if an individual element is already >= k? The shortest subarray length is 1.

## Examples to say out loud
- Consider `nums = [2, -1, 2]` with `k = 3`. The prefix sums are `P = [0, 2, 1, 3]`. At index 3, `P[3] - P[0] = 3 >= 3`, giving length 3. Subarray `[2, -1, 2]` has sum 3, length 3.
- Edge case with negatives: `nums = [-1, -1, 4]` and `k = 4`. The element `4` alone gives sum 4 and length 1, so the result is 1.
- Impossible case: `nums = [1, 2]` and `k = 4`. The total sum is 3 < 4, so return -1.

## Brute force
A brute force approach computes every subarray sum `sum(nums[i..j-1])` using nested loops in O(n^2) time, tracking the minimum length `j - i` where the sum is at least k. With n up to 100,000, an O(n^2) solution runs in 10^10 operations and times out. Standard two-pointer sliding windows fail because expanding or contracting a window with negative values can arbitrarily increase or decrease the sum.

## The key observation
Define the prefix sum array `P` where `P[j] = sum(nums[0..j-1])`. The problem asks for the minimum `j - i` such that `i < j` and `P[j] - P[i] >= k`.
Two crucial monotonic optimizations allow linear time:
1. If `P[j] - P[i] >= k`, any future right boundary `j' > j` paired with index `i` would produce a longer subarray `j' - i > j - i`. Thus, once an index `i` satisfies the condition with the current `j`, `i` will never yield a shorter valid subarray and can be permanently discarded from the front of candidates.
2. If we consider candidate starts `i1 < i2` where `P[i1] >= P[i2]`, the later index `i2` has both a smaller prefix sum (making it easier to reach `k`) and a larger index (yielding shorter length). Hence `i1` is strictly dominated by `i2` and can be popped from the back of candidates.
Maintaining a double-ended queue of indices with strictly increasing prefix sums resolves both requirements.

## Optimal approach
1. Compute prefix sums array `P` of length `n + 1` with 64-bit integers to prevent overflow.
2. Initialize an empty double-ended queue `dq` and `best = n + 1`.
3. Iterate `j` from 0 to `n`:
   - While `dq` is not empty and `P[j] - P[dq.front()] >= k`: record `best = min(best, j - dq.front())` and pop `dq.front()`.
   - While `dq` is not empty and `P[dq.back()] >= P[j]`: pop `dq.back()` because index `j` dominates `dq.back()`.
   - Push `j` onto the back of `dq`.
4. Return `best <= n ? best : -1`.

Complexity:
- Time complexity: O(n) because each index from 0 to n is pushed onto the deque at most once and popped at most once.
- Space complexity: O(n) for the prefix sums array and the monotonic deque storing at most n + 1 indices.

## Code walkthrough
- `vector<long long> p(n + 1, 0)`: Tracks cumulative sums using 64-bit integers to avoid 32-bit overflow when values are large.
- `while (!dq.empty() && p[j] - p[dq.front()] >= k)`: Checks if the window ending at `j - 1` with start `dq.front()` satisfies target `k`. Pops from front to optimize future lengths.
- `while (!dq.empty() && p[dq.back()] >= p[j])`: Enforces monotonically increasing prefix sums in the deque, eliminating dominated starts.
- `dq.push_back(j)`: Appends current index as a prospective left boundary for future indices.

## Test it out loud
- Test `nums = [1], k = 1`:
  - `P = [0, 1]`.
  - At `j = 0`: `dq = [0]`.
  - At `j = 1`: `P[1] - P[0] = 1 >= 1`, `best = min(2, 1 - 0) = 1`, pop 0, push 1.
  - Return 1.
- Test `nums = [84, -37, 32, 40, 95], k = 167`:
  - Tracing prefix sums correctly evaluates candidate subarrays without evaluating every pair, identifying the shortest window of length 3 ending at index 5 with sum >= 167.

## Follow-ups
- Why doesn't standard two-pointer sliding window work? When negative numbers exist, moving the right pointer can decrease the sum and moving the left pointer forward can increase the sum, violating the monotonicity required by standard sliding windows.
- What if all numbers in `nums` were guaranteed positive? Then prefix sums are strictly increasing, allowing a standard two-pointer sliding window in O(1) auxiliary space.

## Common mistakes
- Using 32-bit integers for prefix sums, leading to integer overflow given negative numbers and cumulative values up to 10^9.
- Forgetting to initialize the deque with `0` (or evaluating `j = 0`), which misses subarrays starting at index 0.
- Not popping from the front when a valid sum is found, which degrades worst-case time complexity to O(n^2).
