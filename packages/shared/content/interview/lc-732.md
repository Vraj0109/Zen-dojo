## Clarify first

- Are intervals half-open? (Yes, $[startTime, endTime)$ covering times from $startTime$ up to but not including $endTime$).
- Can bookings overlap arbitrarily without being rejected? (Yes, unlike My Calendar I and II, every booking in My Calendar III is accepted).
- What does `book(startTime, endTime)` return? (Returns the maximum $k$, which is the maximum number of concurrent bookings active at any single moment across all accepted bookings so far).
- What are the constraints on calls and time? ($0 \le startTime < endTime \le 10^9$; at most $400$ calls to `book`).
- Does a booking ending at 10 and another starting at 10 count as an overlap? (No, at timestamp 10 the first has ended and the second has begun, contributing an overlap of 1).

## Examples to say out loud

- Increasing overlap count:
  - `book(10, 20)` $\implies 1$
  - `book(50, 60)` $\implies 1$
  - `book(10, 40)` $\implies 2$ (moments $10$ to $19$ have 2 bookings)
  - `book(5, 15)` $\implies 3$ (moments $10$ to $14$ have 3 bookings simultaneously)
  - `book(5, 10)` $\implies 3$ (max overlap remains 3)
- Nested intervals:
  - `[1, 100], [2, 99], [3, 98], [4, 97], [50, 51]` $\implies$ each nested booking increases peak concurrency by 1, reaching 5.

## Brute force

A naive simulation creates an array of size $10^9$ to count bookings per timestamp. With coordinates up to $10^9$, allocating this array takes 1 GB+ memory and $O(10^9)$ time per booking, which causes Memory Limit Exceeded.
Alternatively, checking intersections between all combinations of intervals takes combinatorial time.

## The key observation

The maximum overlap of a collection of intervals is a classic **sweep-line / difference array** problem.
- A booking $[startTime, endTime)$ increases the number of concurrent events by $+1$ at $startTime$ and decreases it by $-1$ at $endTime$.
- Because timestamps reach $10^9$ while total calls are small ($N \le 400$), we can use a **coordinate-compressed ordered map** (`std::map` in C++, `TreeMap` in Java) storing non-zero deltas.
- On each booking, increment `change[startTime]++` and decrement `change[endTime]--`.
- A prefix sum scan over the ordered map in ascending order of keys traces the exact number of active intervals at any point in time, and the global maximum prefix sum is the answer.

## Optimal approach

1. Maintain an ordered map `change`: mapping `timestamp -> delta`.
2. Operation `book(startTime, endTime)`:
   - Record start event: `change[startTime]++`.
   - Record end event: `change[endTime]--`.
   - Initialize `running = 0` and `best = 0`.
   - Iterate through entries in `change` in ascending order of timestamp:
     - `running += entry.second`.
     - `best = max(best, running)`.
   - Return `best`.

Complexity:
- Time: $O(n)$ time per `book` call, where $n$ is the number of bookings so far ($n \le 400$). Inserting into the map takes $O(\log n)$, and sweeping the $2n$ map entries takes $O(n)$. Over 400 calls, total operations are roughly $\sum_{i=1}^{400} 2i \approx 1.6 \times 10^5$, executing in under 2 milliseconds.
- Space: $O(n)$ auxiliary space to store at most $2n$ entries in the ordered map.

## Code walkthrough

In the reference implementation:
- `map<int, int> change;`: maintains chronological ordering of transition events.
- `change[startTime]++; change[endTime]--;`: difference array representation of range addition $+1$ on $[startTime, endTime)$.
- `running += c.second;`: simulates time sweep, integrating deltas into instantaneous active room/booking count.
- `best = max(best, running);`: tracks the all-time peak concurrent overlap.

## Test it out loud

- Exact touching boundaries: `book(1, 2)` and `book(2, 3)`. At $t = 2$, `change[2]` receives $-1$ from the first and $+1$ from the second, netting $0$. Running count transitions $1 \to 1 \to 0$. Peak remains 1.
- Identical intervals: `book(1, 2)` three times. `change[1] = 3, change[2] = -3`. Peak is 3.
- Large coordinates: `book(0, 1000000000)`. Only two entries `{0: 1, 10^9: -1}` created. Memory and runtime remain minimal.

## Follow-ups

- Can we achieve $O(\log n)$ per `book` call?
  Yes, using a dynamic Segment Tree with lazy propagation over range $[0, 10^9]$. Each range update and max query executes in $O(\log(\text{range}))$, which takes $O(\log(10^9)) \approx 30$ operations per booking.
- How to return the timestamp where the peak occurs?
  Track the map key `c.first` whenever `running > best`.
- What if bookings can be cancelled / removed?
  Decrement `change[startTime]--` and increment `change[endTime]++`, reversing the deltas.

## Common mistakes

- Treating `endTime` as inclusive: placing the $-1$ delta at $endTime + 1$, incorrectly keeping the booking active at timestamp $endTime$.
- Using an unordered hash map: the sweep-line requires processing timestamps in strictly increasing order, which fails without an ordered map or explicit sorting.
- Trying to allocate a static array for coordinates up to $10^9$.
