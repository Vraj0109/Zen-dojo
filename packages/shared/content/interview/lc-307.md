## Clarify first

- What operations must be supported? (Type 1: point update `[1, index, val]` setting `nums[index] = val`. Type 2: range sum query `[2, left, right]` returning $\sum_{i=left}^{right} nums[i]$).
- Are indices 0-based or 1-based? (Input indices are 0-based; $0 \le left \le right < n$).
- Can values or updates be negative? (Yes, $-100 \le nums[i], val \le 100$).
- What are the query and array size bounds? ($n \le 3 \cdot 10^4$ and $q \le 3 \cdot 10^4$).
- Should only type 2 query results be returned? (Yes, return an array containing the outputs of all type 2 sum queries in sequential order).

## Examples to say out loud

- Interleaved update and query: `nums = [1, 3, 5]`, queries: `[2, 0, 2]` $\implies 1 + 3 + 5 = 9$. Then `[1, 1, 2]` changes array to `[1, 2, 5]`. Next `[2, 0, 2]` $\implies 1 + 2 + 5 = 8$. Output is `[9, 8]`.
- Single element updates: `nums = [1]`. Query `[2, 0, 0]` gives 1. Update `[1, 0, 10]` sets index 0 to 10. Query `[2, 0, 0]` gives 10. Output is `[1, 10]`.
- Zero initialized array: `nums = [0, 0, 0]`. Updates and queries reflect point modifications dynamically.

## Brute force

A standard array allows $O(1)$ updates by writing directly to `nums[index] = val`, but each range query takes $O(n)$ by iterating from `left` to `right`. Conversely, a simple prefix sum array answers range queries in $O(1)$, but each update takes $O(n)$ to recompute subsequent prefix values. With $q = 3 \cdot 10^4$ operations on an array of size $3 \cdot 10^4$, either naive choice takes $O(q \cdot n) \approx 9 \times 10^8$ operations, resulting in Time Limit Exceeded.

## The key observation

We need a data structure that balances both point updates and prefix sum queries efficiently. A Binary Indexed Tree (Fenwick tree) or Segment Tree organizes elements hierarchically, allowing both point updates and prefix sum calculations to execute in $O(\log n)$ time. A Fenwick tree uses 1-based indexing where index $i$ is responsible for the range $(i - \text{LSB}(i), i]$. Isolating the lowest set bit with bitwise math `i & -i` gives an implementation that requires only an array of size $n + 1$ and few lines of code.

## Optimal approach

1. Build a 1-indexed Fenwick Tree `tree` of size $n + 1$ initialized to 0.
2. Initialize the tree with elements from `nums`:
   - For each index $i$ from 0 to $n - 1$, call `add(i + 1, nums[i])`.
3. Define helper functions:
   - `add(i, delta)`: while $i \le n$, add `delta` to `tree[i]` and advance $i += i \ \& \ (-i)$.
   - `query(i)`: while $i > 0$, accumulate `tree[i]` and retreat $i -= i \ \& \ (-i)$.
4. Process each query `q`:
   - If `q[0] == 1` (update `[1, idx, val]`):
     - Compute `delta = val - nums[idx]`.
     - Update array record: `nums[idx] = val`.
     - Update tree: `add(idx + 1, delta)`.
   - If `q[0] == 2` (range sum `[2, l, r]`):
     - Compute range sum as `query(r + 1) - query(l)`.
     - Append result to the output list.
5. Return the collected answers.

Complexity:
- Time: Initialization takes $O(n \log n)$ (or $O(n)$ with linear prefix initialization). Each update or query takes $O(\log n)$. Total time is $O(n + q \log n)$, which takes under 20 ms for $3 \cdot 10^4$ operations.
- Space: $O(n)$ auxiliary space to store the Fenwick tree array of size $n + 1$.

## Code walkthrough

In the reference implementation:
- `for (; i <= n; i += i & -i) tree[i] += delta;`: propagates changes up the Fenwick tree using the lowest set bit.
- `for (; i > 0; i -= i & -i) sum += tree[i];`: traverses downward to compute cumulative prefix sums $\sum_{k=1}^i nums[k-1]$.
- `long long delta = val - nums[idx]; nums[idx] = val;`: determines the differential shift rather than resetting the tree from scratch.
- `res.push_back((int)(query(r + 1) - query(l)));`: evaluates range $[l, r]$ by subtracting prefix sum at $l$ from prefix sum at $r + 1$.

## Test it out loud

- Multiple updates on same index: `nums = [5, 10, 15]`. Updates zero out indices 0, 1, and 2. Final query `[2, 0, 2]` correctly sums $0 + 0 + 0 = 0$.
- Negative values: `nums = [-1, -2, -3]`. Sum is $-6$. Update sets index 1 to 2 (`delta = 2 - (-2) = +4`). New sum is $-1 + 2 + (-3) = -2$. Handled correctly.
- Single element: `nums = [1]`. Query `query(1) - query(0)` returns `tree[1] - 0 = 1`.

## Follow-ups

- Can we build the Fenwick tree in $O(n)$ instead of $O(n \log n)$?
  Yes, copy `nums` into `tree` (1-indexed) and for each $i \in [1, n]$, add `tree[i]` to `tree[i + (i & -i)]` if $i + (i & -i) \le n$.
- How does a Segment Tree compare?
  Segment Trees take $4n$ space and have higher constant factor overhead, but they can easily support general associative operations (range min/max, GCD) and range updates with lazy propagation.
- What if range updates (adding to an entire interval $[l, r]$) are also required?
  Use two Fenwick trees (range update, range query BIT) or a Segment Tree with lazy propagation.

## Common mistakes

- Passing `val` instead of `val - nums[idx]` to `add`: Fenwick tree operations are additive, so point updates must supply the difference `delta`.
- Off-by-one errors mixing 0-based array indices with 1-based Fenwick tree indices.
- Forgetting to update `nums[idx] = val` in the base array, causing subsequent updates to the same index to calculate an incorrect delta.
