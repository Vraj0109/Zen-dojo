## Clarify first
- How many piles must be merged in each move? Exactly k consecutive piles must be merged into one single pile.
- What is the cost of a move? The sum of stones in the k consecutive piles being merged.
- What should be returned if it is impossible to reduce the stones into a single pile? Return -1.
- Can piles be reordered? No, only contiguous, consecutive piles can be merged.

## Examples to say out loud
- Standard solvable case: `stones = [3, 2, 4, 1]`, `k = 2`:
  - 4 piles can merge by reducing 1 pile per step (`k - 1 = 1`):
  - Merge [3, 2] -> [5, 4, 1], cost = 5.
  - Merge [4, 1] -> [5, 5], cost = 5.
  - Merge [5, 5] -> [10], cost = 10.
  - Total cost = `5 + 5 + 10 = 20`.
- Impossible case: `stones = [3, 2, 4, 1]`, `k = 3`:
  - Each merge takes 3 piles and produces 1 pile, reducing the total pile count by `k - 1 = 2`.
  - Starting with 4 piles: 4 - 2 = 2 piles. We cannot merge 2 piles because we need exactly 3. Return -1.

## Brute force
A brute force approach simulates all possible choices of k adjacent piles to merge at each step using recursion. Because there are `O(n - k + 1)` choices at the first step, `O(n - 2k + 2)` at the second, and so on, the tree of choices grows exponentially without memoization. Interval Dynamic Programming caches intermediate range reductions.

## The key observation
Each merge reduces the number of piles by exactly `k - 1`.
If we start with n piles and want to end with 1 pile, the total reduction must be `n - 1`.
Therefore, a valid sequence of moves exists if and only if:
`(n - 1) % (k - 1) == 0`.
If this condition does not hold, return -1 immediately.
For interval DP:
Let `dp[i][j]` be the minimum cost to reduce the subarray `stones[i..j]` to the fewest possible piles:
- To merge `stones[i..j]`, we can split the interval into a left part `stones[i..m]` that reduces to 1 pile, and a right part `stones[m + 1..j]` that reduces to the remaining piles.
- The split point `m` must step by `k - 1` (i.e. `m = i, i + (k - 1), i + 2*(k - 1), ...`) so that the left part `stones[i..m]` can legally reduce to 1 pile.
- Once the best split cost `dp[i][j]` is found, if the entire range `stones[i..j]` can itself be merged into 1 pile (i.e. `(j - i) % (k - 1) == 0`), we add the sum of stones in `stones[i..j]` for the final merge step.

## Optimal approach
1. Check feasibility: If `(n - 1) % (k - 1) != 0`, return -1.
2. Precompute prefix sums: `pre[x + 1] = pre[x] + stones[x]` to compute range sums `sum(i..j) = pre[j + 1] - pre[i]` in O(1) time.
3. Allocate an `n x n` DP table `dp` initialized to 0.
4. Iterate interval length `len` from `k` to `n`:
   - For `i` from 0 to `n - len`:
     - Let `j = i + len - 1`.
     - Initialize `dp[i][j] = INF`.
     - For `m` from `i` to `j - 1` stepping by `k - 1`:
       - `dp[i][j] = min(dp[i][j], dp[i][m] + dp[m + 1][j])`.
     - If `(len - 1) % (k - 1) == 0`:
       - `dp[i][j] += pre[j + 1] - pre[i]`.
5. Return `dp[0][n - 1]`.

Complexity:
- Time complexity: O(n^3 / k) because the outer two loops iterate over O(n^2) intervals and the inner split loop steps by `k - 1`, visiting O(n / k) split points. With `n <= 30`, this executes in fewer than 10^5 operations.
- Space complexity: O(n^2) auxiliary space for the `dp` matrix and prefix sums.

## Code walkthrough
- `if ((n - 1) % (k - 1)) return -1`: Instant mathematical check on pile count reducibility.
- `vector<int> pre(n + 1, 0)`: Prefix sum array enabling O(1) interval sum calculations.
- `for (int m = i; m < j; m += k - 1)`: Enforces that the left segment `[i..m]` always reduces to exactly 1 pile.
- `if ((len - 1) % (k - 1) == 0) dp[i][j] += pre[j + 1] - pre[i]`: Adds the cost of the final merge whenever the current interval can collapse into a single pile.
- Returns `dp[0][n - 1]`.

## Test it out loud
- Test `stones = [3, 2, 4, 1], k = 3`:
  - `n = 4, k = 3`. `(4 - 1) % (3 - 1) = 3 % 2 = 1 != 0`.
  - Returns -1 immediately. Correct.
- Test `stones = [7], k = 2`:
  - `(1 - 1) % (2 - 1) = 0`.
  - Loop `len` from 2 to 1 does not run.
  - `dp[0][0] = 0`. Returns 0. Correct.

## Follow-ups
- Why does stepping `m` by `k - 1` suffice instead of using a 3D DP `dp[i][j][p]` (cost to reduce `stones[i..j]` to `p` piles)? Because any reduction to 1 pile can be split into a 1-pile prefix and a `(p - 1)`-pile suffix, reducing state dimensions and avoiding the third parameter `p`.
- How does this relate to Matrix Chain Multiplication? Both are interval DP problems, but here merges require fixed block sizes of k elements rather than pairwise binary splits.

## Common mistakes
- Stepping `m` by 1 instead of `k - 1`, which invalidates the assumption that the left segment can merge into 1 pile.
- Forgetting the final check `(n - 1) % (k - 1) != 0` at the very start.
- Adding the prefix sum `pre[j + 1] - pre[i]` when the interval cannot be merged into 1 pile.
