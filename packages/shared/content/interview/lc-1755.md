## Clarify first

- What is the maximum size of the array? ($1 \le n \le 40$).
- Can elements and the goal be negative? (Yes, $-10^7 \le nums[i] \le 10^7$ and $-10^9 \le goal \le 10^9$).
- Can the chosen subsequence be empty? (Yes, an empty subsequence has a sum of 0).
- Can the sum cause 32-bit integer overflow? (Yes, $40 \times 10^7 = 4 \times 10^8$, which fits in standard 32-bit signed ints, but difference calculations like $|sum - goal|$ can exceed $2 \cdot 10^9$, requiring 64-bit integers like `long long`).
- What exactly are we minimizing? (The absolute difference $|s - goal|$ where $s$ is the sum of any chosen subsequence).

## Examples to say out loud

- Subsequence matches goal exactly: `nums = [5, -7, 3, 5], goal = 6`. Taking subset `[5, 3, -7, 5]` gives sum $6$, $|6 - 6| = 0$.
- Empty subsequence is best: `nums = [1, 2, 3], goal = -7`. All non-empty subsets produce positive sums, which are farther from $-7$ than empty subset sum $0$, giving $|0 - (-7)| = 7$.
- Negative numbers involved: `nums = [7, -9, 15, -2], goal = -5`. Subsequence `[-2, -9, 7]` has sum $-4$, giving difference $|-4 - (-5)| = 1$.

## Brute force

The brute-force method generates all $2^n$ possible subsequences, computes each sum $s$, and tracks $\min |s - goal|$. For $n = 40$, $2^{40} \approx 1.1 \times 10^{12}$ operations, which severely exceeds the standard 1-second execution limit.

## The key observation

While $n = 40$ is too large for $O(2^n)$, $n/2 = 20$ is completely manageable since $2^{20} \approx 10^6$. We apply the meet-in-the-middle technique: partition `nums` into two halves of size at most 20, compute all subset sums for both halves independently, and sort the second half. For each sum $x$ from the first half, we want a companion sum $y$ from the second half such that $x + y \approx goal$, which means $y \approx goal - x$. We can find the best $y$ in $O(\log(2^{n/2}))$ using binary search (`std::lower_bound`).

## Optimal approach

1. Split `nums` into two halves: `left` of size $\lfloor n/2 \rfloor$ and `right` of size $\lceil n/2 \rceil$.
2. Generate all subset sums for each half:
   - Start with `[0]`. For each number in the half, append `existing_sum + number` to the list.
   - Let `s1` be the sums of `left` and `s2` be the sums of `right`.
3. Sort `s2` in ascending order and optionally remove duplicates to speed up queries.
4. Initialize `best = |goal|` (representing the empty subset where both halves contribute 0).
5. For each sum $x$ in `s1`:
   - Compute `target = goal - x`.
   - Use binary search (`lower_bound`) in `s2` to locate the first element $y \ge target$.
   - If $y$ exists, update `best = min(best, |x + y - goal|)`.
   - Also check the predecessor of $y$ in `s2` (the largest element $< target$), updating `best` if closer.
6. Return `best`.

Complexity:
- Time: `O(n * 2^(n/2))` where generating subset sums takes $O(2^{n/2})$, sorting `s2` takes $O((n/2) \cdot 2^{n/2})$, and binary searching for each element in `s1` takes $O(2^{n/2} \cdot \log(2^{n/2})) = O((n/2) \cdot 2^{n/2})$.
- Space: `O(2^(n/2))` auxiliary space to store the $2^{20} \approx 10^6$ subset sums.

## Code walkthrough

In the reference implementation:
- `getSums(left, s1)`: iteratively doubles the size of `out` by adding the current number to all previous sums.
- `sort(s2.begin(), s2.end()); s2.erase(unique(...), s2.end());`: prepares the second half for binary search.
- `auto it = lower_bound(s2.begin(), s2.end(), target);`: finds the smallest sum $\ge target$.
- `if (it != s2.end()) best = min(best, llabs(x + *it - goal));`: checks the candidate $\ge target$.
- `if (it != s2.begin()) best = min(best, llabs(x + *prev(it) - goal));`: checks the closest candidate $< target$.

## Test it out loud

- Zero elements chosen: `nums = [10000000], goal = 10000000`. Choosing `[10000000]` yields sum $10^7$, difference 0.
- All negative numbers: `nums = [-5, -3, -1], goal = -4`. Subsets evaluate combinations like `[-3, -1]` summing to $-4$, yielding $| -4 - (-4) | = 0$.
- Single element: `nums = [0], goal = 0`. Handled gracefully by `mid = 0`, generating `s1 = [0]` and `s2 = [0, 0]`, returning 0.

## Follow-ups

- Can we avoid binary search using two pointers?
  Yes, if both `s1` and `s2` are sorted, we can place one pointer at the start of `s1` and another at the end of `s2`, moving them inward in $O(2^{n/2})$ time after sorting.
- How does this differ from the 0/1 Knapsack problem?
  In 0/1 Knapsack, item weights and target are typically positive and bounded by a small integer $W$, allowing pseudo-polynomial $O(n W)$ DP. Here, values are up to $10^7$ and $goal$ up to $10^9$, making DP on values impossible.
- What if we need to return the actual elements rather than just the minimum difference?
  Store bitmasks alongside each sum indicating which indices were picked from the left and right halves.

## Common mistakes

- Using 32-bit signed integer for subtraction: `x + *it - goal` can overflow `INT_MIN` / `INT_MAX`, causing undefined behavior. Use `long long` and `llabs`.
- Forgetting to check the predecessor `prev(it)` when `it` points to a value strictly greater than `target`; the predecessor might be closer to `goal`.
- Trying DP with array sizing based on `goal`, which fails due to negative values and magnitudes up to $10^9$.
