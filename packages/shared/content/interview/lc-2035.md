## Clarify first

- What is the total length of the array? (The length is $2n$ where $1 \le n \le 15$, so array length is at most 30).
- Must the two partitioned arrays have identical size? (Yes, each must contain exactly $n$ elements).
- Can the elements be negative or zero? (Yes, $-10^7 \le nums[i] \le 10^7$).
- What are we minimizing? (The absolute difference $|\text{sum}_1 - \text{sum}_2|$).
- Does the order of elements matter? (No, elements are partitioned into any two subsets of size $n$).

## Examples to say out loud

- Equal partition: `nums = [1, 2, 3, 4]`. $2n = 4 \implies n = 2$. Total sum is 10. We can partition into `[1, 4]` (sum 5) and `[2, 3]` (sum 5), giving difference $|5 - 5| = 0$.
- Unequal minimum difference: `nums = [3, 9, 7, 3]`. Partitioning into `[3, 9]` (sum 12) and `[7, 3]` (sum 10) gives difference $|12 - 10| = 2$.
- Negative values: `nums = [-36, 36]`. $n = 1$. The only partition is `[-36]` and `[36]`, giving difference $|-36 - 36| = 72$.

## Brute force

A naive approach generates all combinations of picking $n$ elements from $2n$. The number of such combinations is $\binom{2n}{n}$. For $n = 15$, $\binom{30}{15} = 155,117,520$. Evaluating over $1.5 \times 10^8$ combinations in Python or C++ within strict time limits is prone to TLE, especially when computing subset sums from scratch.

## The key observation

Let $total$ be the sum of all elements. If subset 1 has sum $S$, subset 2 has sum $total - S$, and the difference is $|total - 2S|$. We want $S \approx total / 2$. Split the array into two halves of size $n$: `left` and `right`. If we choose $k$ elements from `left`, we must choose exactly $n - k$ elements from `right`. By grouping the subset sums of each half by the count of elements chosen ($k \in [0, n]$), we can sort `right[n - k]` and use binary search to find the sum closest to $(total - 2 \cdot s_1) / 2$ for each $s_1 \in left[k]$.

## Optimal approach

1. Calculate $total = \sum nums$. Split `nums` into `left` of size $n$ and `right` of size $n$.
2. For each mask from $0$ to $2^n - 1$:
   - Let $k = \text{popcount}(mask)$.
   - Compute the subset sum $s_1$ using elements from `left` where the corresponding bit is set, and add $s_1$ to `left[k]`.
   - Compute the subset sum $s_2$ using elements from `right` where the corresponding bit is set, and add $s_2$ to `right[k]`.
3. For each $k \in [0, n]$, sort `right[k]`.
4. Initialize `ans = LLONG_MAX`.
5. For each $k \in [0, n]$:
   - Let $need = n - k$.
   - For each sum $s_1$ in `left[k]`:
     - The ideal $s_2$ minimizes $|total - 2(s_1 + s_2)|$, so target $s_2 \approx (total - 2 s_1) / 2$.
     - Use binary search (`lower_bound`) on `right[need]` to find the first element $\ge target$.
     - If it exists, update `ans = min(ans, |total - 2(s_1 + s_2)|)`.
     - Also check the predecessor in `right[need]` (if available) and update `ans`.
6. Return `ans`.

Complexity:
- Time: `O(n * 2^n)` because generating subsets takes $O(n \cdot 2^n)$, sorting each bucket $\sum \binom{n}{k} \log \binom{n}{k} \le O(n \cdot 2^n)$, and binary searching across all pairs takes $\sum \binom{n}{k} \log \binom{n}{n-k} \le O(n \cdot 2^n)$. For $n = 15$, $15 \cdot 32768 \approx 5 \times 10^5$ operations, running in well under 0.1 seconds.
- Space: `O(2^n)` auxiliary space to store all subset sums grouped into lists of size $\binom{n}{k}$.

## Code walkthrough

In the reference implementation:
- `long long total = accumulate(nums.begin(), nums.end(), 0LL);`: uses 64-bit integers to prevent overflow during sum computation.
- `int cnt = __builtin_popcount(mask);`: categorizes each subset by the exact count of items picked.
- `sort(right[k].begin(), right[k].end());`: orders candidate sums of size $k$ from the right half for binary search.
- `int need = n - k;`: enforces that total items chosen across both halves equals exactly $n$.
- `auto it = lower_bound(right[need].begin(), right[need].end(), target);`: identifies the closest matching sum.

## Test it out loud

- All zeros: `nums = [0, 0, 0, 0]`. $n = 2$. Total sum is 0. All subset sums are 0. $|0 - 0| = 0$ returned immediately.
- Positive and negative cancel: `nums = [100, -100, 50, -50]`. Total is 0. Choosing `[100, -100]` yields sum 0; remaining elements `[50, -50]` have sum 0. Output 0.
- Symmetric array: `nums = [2, -1, 0, 4, -2, -9]`. $n = 3$, correctly matches combinations to find identical half-sums if possible.

## Follow-ups

- What if $nums[i] \ge 0$ and values are small?
  If values are small, pseudo-polynomial dynamic programming (0/1 Knapsack with subset size constraint) could be used with state `dp[count][sum]`. But with values up to $10^7$, meet-in-the-middle is required.
- Can two pointers replace binary search?
  Yes, iterating $s_1$ in sorted order allows a two-pointer crawl over sorted `right[need]` in $O(\binom{n}{k})$ time, saving the logarithmic factor.
- What if $2n$ was up to 40 instead of 30?
  $n = 20 \implies 2^{20} \approx 10^6$ per half, which would push runtime to $\approx 2 \times 10^7$ operations, still within typical limits with fast I/O.

## Common mistakes

- Forgetting the equal-size constraint ($n$ elements per partition) and matching any subset sum from the right half regardless of element count.
- Integer division truncation when computing `target = (total - 2 * s1) / 2`: must check both `it` and `prev(it)` because integer division rounds towards zero.
- Overflow in calculating `total - 2 * (s1 + s2)` when using 32-bit `int`.
