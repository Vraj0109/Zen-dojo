## Clarify first
- How does water rise over time? At time `t`, water depth is `t`, meaning any cell with `grid[i][j] <= t` is submerged and can be moved across instantly.
- What are the starting and ending positions? Start at `(0, 0)` at time 0 and reach `(n - 1, n - 1)`.
- What is the value distribution in the grid? Distinct integers from 0 to `n * n - 1`.
- Can you move in all 4 cardinal directions? Yes, up, down, left, and right.

## Examples to say out loud
- Consider 2x2 grid `[[0, 2], [1, 3]]`:
  - Starting cell `(0, 0)` has elevation 0.
  - Path `(0,0) -> (1,0) -> (1,1)` visits elevations 0, 1, 3.
  - The destination has elevation 3, so you cannot step onto it until time 3. Output: 3.
- Example where an indirect path is faster: `[[0, 3], [1, 2]]`.
  - Direct step `(0,0) -> (0,1)` requires waiting until time 3.
  - Path `(0,0) -> (1,0) -> (1,1)` visits elevations `0, 1, 2`, requiring time 2. Output: 2.

## Brute force
A brute force approach searches every possible path from top-left to bottom-right using backtracking DFS, calculating the maximum elevation along each path and taking the minimum across all paths. On an n x n grid, the number of self-avoiding walks is exponential, making brute force intractable. Alternatively, binary searching on time `t` in `[0, n * n - 1]` with a flood fill takes O(n^2 log n). Dijkstra's algorithm solves it directly and optimally.

## The key observation
To reach the bottom-right cell, the required time is determined by the bottleneck: the maximum elevation encountered along the chosen route.
The problem is equivalent to finding a path from `(0, 0)` to `(n - 1, n - 1)` that minimizes the maximum cell elevation along the path.
Using Dijkstra's algorithm:
- Define the cost to reach a cell as `max(time_so_far, grid[nx][ny])`.
- Use a min-heap to always expand the reachable frontier cell with the lowest water level requirement.
- The first time the destination cell `(n - 1, n - 1)` is popped from the min-heap, its associated time is the exact minimum time required.

## Optimal approach
1. Initialize an `n x n` boolean array `seen` with all entries false.
2. Initialize a min-heap priority queue `pq` of tuples `{time, x, y}`.
3. Push `{grid[0][0], 0, 0}` into `pq` and mark `seen[0][0] = true`.
4. While `pq` is not empty:
   - Pop `{t, x, y}` with the smallest `t`.
   - If `x == n - 1` and `y == n - 1`, return `t`.
   - For each of the 4 cardinal neighbors `(nx, ny)`:
     - If `(nx, ny)` is within grid boundaries and `!seen[nx][ny]`:
       - Mark `seen[nx][ny] = true`.
       - Compute required time: `nt = max(t, grid[nx][ny])`.
       - Push `{nt, nx, ny}` into `pq`.
5. Return -1 if unreachable (impossible under problem constraints).

Complexity:
- Time complexity: O(n^2 log n) where n^2 is the number of cells. Each cell is pushed and popped from the priority queue at most once.
- Space complexity: O(n^2) auxiliary space for the `seen` matrix and the priority queue.

## Code walkthrough
- `pq.push({grid[0][0], 0, 0})`: Seeds the queue with the starting cell's intrinsic elevation.
- `if (x == n - 1 && y == n - 1) return t`: Guarantees optimal bottleneck time when destination is dequeued.
- `seen[nx][ny] = true`: Marks visited immediately upon enqueueing to prevent duplicate insertions into the heap.
- `pq.push({max(t, grid[nx][ny]), nx, ny})`: Extends path by taking the maximum between the cumulative bottleneck time and the neighbor's elevation.

## Test it out loud
- Test single cell `[[0]]`:
  - Pushes `{0, 0, 0}`.
  - Pops `{0, 0, 0}`. `x == 0 && y == 0`, returns 0 immediately. Correct.
- Test `[[0, 1], [2, 3]]`:
  - `(0, 0)` popped at `t = 0`. Neighbors `(0, 1)` with `t = 1` and `(1, 0)` with `t = 2` enqueued.
  - `(0, 1)` popped at `t = 1`. Neighbor `(1, 1)` enqueued with `max(1, 3) = 3`.
  - Next smallest popped is `(1, 0)` at `t = 2`.
  - Next popped is `(1, 1)` at `t = 3`. Returns 3. Correct.

## Follow-ups
- Can we solve this using Union-Find (Kruskal's algorithm)? Yes, sort all cells by elevation from 0 to `n*n - 1`. Add cells one by one to the grid and union them with adjacent already-added neighbors. The elevation of the cell that connects `(0, 0)` and `(n-1, n-1)` into the same set is the answer.
- How does the binary search approach compare? Binary searching `t` in `[0, n*n - 1]` and running BFS has runtime O(n^2 log(n^2)) = O(n^2 log n), which has similar theoretical efficiency and is easy to implement.

## Common mistakes
- Not taking `grid[0][0]` into account initially, assuming start time is 0 even if the starting cell elevation is high.
- Marking nodes visited when popping instead of when pushing, which causes redundant entries in the priority queue.
- Confusing path length with maximum elevation.
