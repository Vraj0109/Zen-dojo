## Clarify first
- What defines a reverse pair? A pair of indices `(i, j)` such that `i < j` and `nums[i] > 2 * nums[j]`.
- Can numbers be negative? Yes, values range from -2^31 to 2^31 - 1.
- Can `2 * nums[j]` overflow a 32-bit signed integer? Yes, values close to integer limits will overflow standard 32-bit types, so 64-bit integer arithmetic (`long long`) is required.
- What if the array has length 1? No pairs exist, so the result should be 0.

## Examples to say out loud
- Consider `nums = [1, 3, 2, 3, 1]`.
  - Pairs where `nums[i] > 2 * nums[j]`:
    - `i = 1 (val 3)` and `j = 4 (val 1)`: `3 > 2 * 1 = 2`.
    - `i = 3 (val 3)` and `j = 4 (val 1)`: `3 > 2 * 1 = 2`.
  - Total valid pairs: 2.
- Negative example: `nums = [-5, -5]`.
  - `i = 0 (val -5)` and `j = 1 (val -5)`: `-5 > 2 * (-5) = -10`. This is true, so output is 1.

## Brute force
A brute force approach evaluates every pair `(i, j)` with `0 <= i < j < n` using nested loops. For each pair, it tests whether `(long long)nums[i] > 2LL * nums[j]` and increments a counter. With n up to 50,000, there are roughly `1.25 * 10^9` pairs, which severely exceeds typical time limits. We can reduce runtime to O(n log n) by embedding the counting step within merge sort.

## The key observation
Just like counting standard inversions, the array can be divided into left and right halves. If both halves are recursively sorted, any reverse pair `(i, j)` either:
1. Lies entirely within the left half.
2. Lies entirely within the right half.
3. Has `i` in the left half and `j` in the right half (a cross pair).
For cross pairs, because both halves are already sorted, as the pointer `i` in the left half advances, `nums[i]` increases. Therefore, the pointer `j` in the right half that satisfies `nums[i] > 2 * nums[j]` only moves forward monotonically. This allows counting all cross pairs for a given merge step in O(length) time before performing the standard merge.

## Optimal approach
1. Define a recursive helper `count(nums, tmp, lo, hi)` that sorts `nums[lo..hi)` and returns the count of reverse pairs.
2. Base case: If `hi - lo <= 1`, return 0.
3. Divide: compute `mid = (lo + hi) / 2`.
4. Recursively count pairs in both halves: `res = count(lo, mid) + count(mid, hi)`.
5. Count cross pairs:
   - Initialize pointer `j = mid`.
   - For each `i` from `lo` to `mid - 1`:
     - Advance `j` while `j < hi` and `(long long)nums[i] > 2LL * nums[j]`.
     - Add `j - mid` to `res`.
6. Merge the two sorted halves into `tmp` and copy back to `nums[lo..hi)`.
7. Return `res`.

Complexity:
- Time complexity: O(n log n) because dividing takes O(log n) levels, and both counting and merging at each level run in O(n) total time.
- Space complexity: O(n) auxiliary space for the temporary merge buffer.

## Code walkthrough
- `long long res = count(a, tmp, lo, mid) + count(a, tmp, mid, hi)`: Recursively tallies internal pairs in both sorted subproblems.
- `for (int i = lo; i < mid; i++)`: Iterates through the sorted left half.
- `while (j < hi && (long long)a[i] > 2LL * a[j]) j++`: Advances `j` monotonically through the sorted right half.
- `res += j - mid`: Adds the number of valid `j` indices matching the current `i`.
- `merge(..., tmp.begin() + lo)` and `copy(...)`: Merges both halves so the segment remains sorted for parent recursive frames.

## Test it out loud
- Test `nums = [5, 1]`:
  - Split into `[5]` and `[1]`.
  - Cross count: `i = 0 (val 5)`. `5 > 2 * 1 = 2` holds, `j` increments to 2.
  - `res += 2 - 1 = 1`.
  - Merge into `[1, 5]`. Returns 1. Correct.
- Test `nums = [2, 2, 2]`:
  - Any pair comparison gives `2 > 2 * 2 = 4`, which is false. Returns 0. Correct.

## Follow-ups
- Can this problem be solved using a Binary Indexed Tree (Fenwick tree) or Segment Tree? Yes, by coordinate compressing all values of `nums[i]` and `2 * nums[i]`, then iterating from right to left while querying prefix frequencies in O(n log n).
- Why must counting happen before merging? Because the condition `nums[i] > 2 * nums[j]` differs from the standard sorting condition `nums[i] > nums[j]`, so counting cannot be piggybacked directly inside the standard single merge loop.

## Common mistakes
- Doubling `nums[j]` as a 32-bit integer, causing signed integer overflow on values near -2^31 or 2^31 - 1.
- Resetting `j = mid` inside the `i` loop, which makes counting O(n^2) rather than taking advantage of two pointers.
- Modifying the array during counting before completing comparisons for all `i`.
