## Clarify first

- What time window does the hit counter measure? (The past 5 minutes, which corresponds to the past 300 seconds: $timestamp - 300 < t \le timestamp$).
- Do calls arrive in chronological order? (Yes, the problem guarantees that calls to `hit` and `getHits` have monotonically non-decreasing timestamps).
- Can multiple hits occur at the exact same timestamp? (Yes, multiple hits may occur at the same second).
- What is the granularity of timestamps? (Seconds granularity; timestamps are positive integers up to $2 \cdot 10^9$).
- What are the call limits? (Up to 300,000 calls to `hit` and `getHits`).

## Examples to say out loud

- Window expiration walkthrough:
  - `hit(1)`, `hit(2)`, `hit(3)`
  - `getHits(4)` $\implies$ all 3 hits fall within $(4 - 300, 4]$, returns 3.
  - `hit(300)` $\implies$ total 4 hits recorded.
  - `getHits(300)` $\implies$ window is $(0, 300]$; hits at 1, 2, 3, 300 all count, returns 4.
  - `getHits(301)` $\implies$ window is $(1, 301]$; hit at 1 has expired ($1 \le 301 - 300$), so only 2, 3, 300 remain; returns 3.

## Brute force

A naive approach appends every hit timestamp into an unbounded dynamic array. On each `getHits(timestamp)`, it iterates from the beginning of the array, counting how many elements satisfy $t > timestamp - 300$. With up to 300,000 calls, scanning the full list on every `getHits` takes $O(N)$ per query, resulting in $O(N^2) \approx 9 \times 10^{10}$ operations and severe Time Limit Exceeded.

## The key observation

Because timestamps arrive in monotonically increasing order:
1. Incoming hits always enter at the newest edge of time.
2. Expired hits always leave from the oldest edge of time.
This matches a **First-In, First-Out (FIFO) queue**.
Whenever `getHits(timestamp)` is called, any timestamp at the front of the queue that is $\le timestamp - 300$ has permanently expired and will never be valid for any future query. By popping expired elements from the front of the queue, the remaining queue size is precisely the count of active hits in the past 300 seconds.

## Optimal approach

1. Maintain a FIFO queue `queue<int> q` storing hit timestamps.
2. Operation `hit(timestamp)`:
   - Push `timestamp` into `q`.
3. Operation `getHits(timestamp)`:
   - While `q` is not empty and `q.front() <= timestamp - 300`:
     - Pop the expired element: `q.pop()`.
   - Return `q.size()`.

Complexity:
- Time: `hit` runs in $O(1)$ time. `getHits` runs in $O(1)$ amortized time, because each hit timestamp is pushed to the queue once and popped at most once across the entire lifetime of the system.
- Space: $O(W)$ auxiliary space where $W$ is the number of hits received within any rolling 300-second window (at most 300,000 elements).

## Code walkthrough

In the reference implementation:
- `queue<int> q;`: stores chronological stream of hit events.
- `q.push(timestamp);`: records each arrival in $O(1)$.
- `while (!q.empty() && q.front() <= timestamp - 300) q.pop();`: evicts expired events from the head of the sliding window.
- `return q.size();`: reports the current valid hit count in $O(1)$.

## Test it out loud

- Burst at same second: `hit(10)` called 3 times. `getHits(10)` returns 3. `getHits(309)` returns 3. `getHits(310)` pops all three, returns 0.
- No hits recorded: `getHits(1)` and `getHits(300)` on a fresh counter return 0.
- Large gaps between queries: `hit(100)`, `hit(200)`, then `getHits(900)`. All items are popped in the loop, returning 0 without errors.

## Follow-ups

- What if millions of hits arrive in the same second (scaling for high write throughput)?
  A raw queue would grow to millions of elements. Instead, use a **circular array of 300 buckets**, each storing `pair<int, int>` for `(timestamp, hit_count)`. Indexing by `timestamp % 300` caps space to strictly $O(1)$ (300 buckets) and aggregates simultaneous hits in $O(1)$ time.
- How to make the circular bucket approach thread-safe?
  Use atomic integers or bucket-level locks / striped mutexes across the 300 buckets so concurrent threads can increment counts without contention.
- How to support distributed hit counting across multiple servers?
  Each server maintains local circular buffers; a central aggregator or Redis sliding-window counter merges bucket sums periodically.

## Common mistakes

- Using `<` instead of `<=` in `q.front() <= timestamp - 300`: hits occurring at exactly $timestamp - 300$ are outside the open interval $(timestamp - 300, timestamp]$ and must be popped.
- Not handling multiple hits at the same timestamp.
- Attempting to binary search an unbounded list without trimming old entries, leading to unbounded memory growth.
