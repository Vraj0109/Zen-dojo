## Clarify first

- What is the initial value of elements in the array? (All elements start initialized to 0 at snap id 0).
- What does `snap()` return? (Returns the current `snap_id`, starting at 0 and incrementing by 1 on each call).
- Can the same index be modified multiple times between two `snap()` calls? (Yes, multiple `set` calls within the same snapshot epoch should overwrite the value for that snapshot).
- What are the scale constraints? ($length \le 50,000$, and up to $100,000$ operations in total).
- Does `get(index, snap_id)` ever ask for a `snap_id` that hasn't been taken yet? (Constraints guarantee $0 \le snap\_id < \text{total snaps taken}$).

## Examples to say out loud

- Basic snapshot tracking:
  - `SnapshotArray(3)`: Array of size 3 initialized to 0.
  - `set(0, 5)`
  - `snap()` $\implies$ returns snapshot id 0.
  - `set(0, 6)`
  - `get(0, 0)` $\implies$ returns 5 (value of index 0 when snapshot 0 was recorded).
  - Snapshot id 0 retains 5 even though current value of index 0 is 6.
- Multiple snaps without sets:
  - `snap()` returns 1, `snap()` returns 2.
  - `get(0, 1)` and `get(0, 2)` both return 6.

## Brute force

A naive implementation makes a full copy of the entire array on every `snap()` call (e.g. `vector<vector<int>> snapshots`). With `length = 50,000` and up to $50,000$ snapshots, copying the array requires $O(length)$ per `snap`, consuming up to $50,000 \times 50,000 = 2.5 \times 10^9$ integers ($\approx 10$ GB RAM), causing Memory Limit Exceeded and Time Limit Exceeded.

## The key observation

Most indices are not modified in every snapshot. Instead of storing a full array copy for each snapshot, record history **per index**.
- For each index $i \in [0, length - 1]$, maintain a list of pairs: `(snap_id, value)`.
- Initialized with `(0, 0)` for all indices.
- When `set(index, val)` is called, check the current `snap_id`: if the last entry for that index already matches `snap_id`, overwrite it in-place; otherwise, append `{snap_id, val}`.
- Because `snap_id` values grow monotonically, each index's history list is inherently sorted by `snap_id`.
- `get(index, snap_id)` simply binary searches the index's history list for the latest entry with $id \le snap\_id$.

## Optimal approach

1. Maintain:
   - `int snaps = 0`: tracks the current snapshot counter.
   - `vector<vector<pair<int, int>>> history`: initialized to size `length`, where each index holds `vector<pair<int, int>>{{0, 0}}`.
2. Operation `set(index, val)`:
   - Access `h = history[index]`.
   - If `h.back().first == snaps`, overwrite `h.back().second = val`.
   - Else, append `{snaps, val}`.
3. Operation `snap()`:
   - Return `snaps++`.
4. Operation `get(index, snap_id)`:
   - Access `h = history[index]`.
   - Perform an upper-bound binary search to find the first entry with `snap_id_entry > snap_id`.
   - The valid snapshot state is the element right before it: `h[lo - 1].second`.

Complexity:
- Time: `set` takes $O(1)$ time. `snap` takes $O(1)$ time. `get` takes $O(\log S)$ time where $S$ is the number of distinct snapshot updates applied to that specific index.
- Space: $O(length + U)$ total space where $U$ is the number of distinct `set` updates across different snapshot epochs.

## Code walkthrough

In the reference implementation:
- `history(length, vector<pair<int, int>>{{0, 0}})`: initializes all cells to 0 at snap 0 so binary search always finds a valid predecessor.
- `if (h.back().first == snaps) h.back().second = val;`: coalesces multiple sets in the same epoch to avoid redundant history nodes.
- `int snap() { return snaps++; }`: snapshot generation runs in pure $O(1)$ without touching the array.
- `int mid = (lo + hi) / 2; if (h[mid].first <= snap_id) lo = mid + 1; else hi = mid;`: upper-bound binary search.
- `return h[lo - 1].second;`: returns the value active at `snap_id`.

## Test it out loud

- Snap before any set: `SnapshotArray(1)`, `snap()` returns 0. `get(0, 0)` searches `[(0, 0)]`, returns 0.
- Overwrite in same snap: `set(0, 4)`, `set(0, 5)`, `set(0, 6)`. Index 0 has only one entry `(0, 6)`. `snap()` returns 0. `get(0, 0)` returns 6.
- Non-consecutive sets: Set index 0 at snap 0 and snap 5. Queries for snaps 1, 2, 3, 4 return the snap 0 value via `lo - 1`.

## Follow-ups

- What if we need to rollback / revert to a previous snapshot?
  Pop historical entries with `snap_id > target_snap`, or create a new snapshot that points backwards.
- How does this relate to persistent data structures?
  This is a partially persistent array. Full persistence (branching snapshots) can be implemented using a persistent segment tree with path copying in $O(\log n)$ per update.
- What if `length` was $10^9$ and queries were sparse?
  Replace the outer `vector` with an `unordered_map<int, vector<pair<int, int>>>` to support sparse indices.

## Common mistakes

- Copying the full array in `snap()`, triggering memory limit exceeded.
- Forgetting to overwrite `h.back()` when multiple sets happen in the same snapshot epoch, creating duplicate snap ids and corrupting binary search.
- Forgetting the initial `(0, 0)` baseline, causing binary search out-of-bounds errors on indices that were never explicitly updated.
