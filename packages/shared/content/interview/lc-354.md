## Clarify first

- Can envelopes be rotated? No, rotation is explicitly forbidden; width must nest inside width, and height inside height.
- Does strict nesting apply to both dimensions? Yes, envelope A fits into envelope B only if `A.width < B.width` AND `A.height < B.height`.
- Can envelopes have identical dimensions? Yes, but two envelopes with the same width (or height) cannot nest inside each other.
- What are the constraints? `envelopes.length <= 100,000`, with dimensions up to 100,000.

## Examples to say out loud

- Chain of envelopes: `envelopes = [[5, 4], [6, 4], [6, 7], [2, 3]]`.
  - Nested sequence: `[2, 3] -> [5, 4] -> [6, 7]`.
  - Notice `[6, 4]` and `[6, 7]` have the same width, so only one of them can be picked.
  - Maximum nested envelopes = 3.
- Equal dimensions edge case: `envelopes = [[1, 1], [1, 1], [1, 1]]`. None can fit inside another, returns 1.
- Two envelopes: `envelopes = [[1, 1], [2, 2]]`. `[1, 1]` fits in `[2, 2]`, returns 2.

## Brute force

A brute-force strategy models envelopes as vertices in a directed acyclic graph (DAG) where a directed edge exists from A to B if A fits inside B. Finding the longest path in this DAG using topological sort or dynamic programming requires constructing all valid edges. In the worst case, comparing all pairs takes `O(n^2)` time. For `n = 100,000`, quadratic time requires `10^{10}` operations and times out.

## The key observation

We have two dimensions: width and height. We can eliminate one dimension by sorting envelopes ascending by width.
Now, what about ties in width? If two envelopes have the same width `w`, neither can fit inside the other. If we sort heights in **descending** order whenever widths tie, then among envelopes with the same width, height will strictly decrease.
When we subsequently find the Longest Increasing Subsequence (LIS) on the height dimension, an increasing subsequence can **never** pick two envelopes with the same width, because their heights appear in decreasing order!
This reduces the 2D problem to 1D LIS on heights, which is solvable in `O(n log n)` time via patience sorting.

## Optimal approach

1. Sort `envelopes` primarily by width in ascending order; on equal widths, sort height in descending order:
   `a[0] != b[0] ? a[0] < b[0] : a[1] > b[1]`.
2. Extract the heights and find the length of the Longest Increasing Subsequence using patience sorting:
   a. Maintain an array `tails`.
   b. For each envelope `e`:
      - Binary search for the first element in `tails` that is `>= e[1]` (using `lower_bound`).
      - If no such element exists, append `e[1]` to `tails`.
      - Otherwise, replace that element with `e[1]`.
3. Return the size of `tails`.

Complexity:
- Time: `O(n log n)` because sorting takes `O(n log n)` and the LIS binary search takes `O(n log n)` across `n` envelopes.
- Space: `O(n)` auxiliary space for the `tails` array.

## Code walkthrough

In the reference implementation:
- `sort(envelopes.begin(), envelopes.end(), [](auto& a, auto& b) { return a[0] != b[0] ? a[0] < b[0] : a[1] > b[1]; });`: sorts width ascending, and critically, height descending on ties.
- `vector<int> tails;`: holds the minimum tail values for increasing height subsequences.
- `auto it = lower_bound(tails.begin(), tails.end(), e[1]);`: binary searches for the replacement position in logarithmic time.
- `if (it == tails.end()) tails.push_back(e[1]); else *it = e[1];`: updates or extends the patience sorting table.
- `return (int)tails.size();`: yields the maximum nesting depth.

## Test it out loud

- `envelopes = [[5, 4], [6, 4], [6, 7], [2, 3]]`:
  - Sorted: `[2, 3]`, `[5, 4]`, `[6, 7]`, `[6, 4]` (note `[6, 7]` precedes `[6, 4]`).
  - Heights: `[3, 4, 7, 4]`.
  - Process 3: `tails = [3]`.
  - Process 4: `tails = [3, 4]`.
  - Process 7: `tails = [3, 4, 7]`.
  - Process 4: replace 7 with 4 -> `tails = [3, 4, 4]`. (Doesn't extend length).
  - Length is 3. Output is 3.

## Follow-ups

- Why is the descending height tie-breaker essential?
  If sorted ascending on ties `[6, 4], [6, 7]`, LIS on heights would pick both 4 and 7, falsely assuming `[6, 4]` can nest inside `[6, 7]` when their widths are identical.
- How would this generalize to 3 dimensions (boxes: width, height, depth)?
  Sorting can eliminate 1 dimension, but the remaining 2 dimensions require a 2D Range Tree or CDQ divide-and-conquer in `O(n log^2 n)` time.

## Common mistakes

- Sorting heights ascending on width ties, which allows envelopes with the same width to nest inside each other.
- Using an `O(n^2)` dynamic programming LIS approach, which times out for `n = 100,000`.
- Using `upper_bound` instead of `lower_bound`, which allows duplicate heights to chain together.
