## Clarify first

- Are the indices `left` and `right` inclusive? (Yes, sum elements from `nums[left]` through `nums[right]` inclusive).
- Can the elements of `nums` be negative? (Yes, $-10^5 \le nums[i] \le 10^5$).
- Can the array be modified after initialization? (No, this is the immutable variant; `nums` remains static).
- How many elements and queries are expected? (Both `nums.length` and `queries.length` up to $10^4$).
- Can the sum exceed 32-bit signed integer limits? (With $n \le 10^4$ and $|nums[i]| \le 10^5$, max absolute sum is $10^9$, fitting within standard 32-bit signed integers).

## Examples to say out loud

- General range: `nums = [-2, 0, 3, -5, 2, -1]`, query `[0, 2]`. Elements are $-2 + 0 + 3 = 1$.
- Range spanning across negatives: Query `[2, 5]` on above array gives $3 + (-5) + 2 + (-1) = -1$.
- Entire array: Query `[0, 5]` gives $(-2) + 0 + 3 + (-5) + 2 + (-1) = -3$.
- Single element range: Query `[1, 1]` on `[1, 1, 1, 1, 1]` returns $1$.

## Brute force

A naive brute-force loops from index `left` to `right` for each query, accumulating the sum element by element. In the worst case where each query asks for the sum of the entire array, answering each query takes $O(n)$ time. For $q$ queries, total time is $O(q \cdot n)$. With $n = 10^4$ and $q = 10^4$, this requires $10^8$ operations, which is unnecessarily redundant for a static array.

## The key observation

The sum of elements in a sub-range `nums[left..right]` can be rewritten as the difference between two prefix sums:
$\sum_{i=left}^{right} nums[i] = \sum_{i=0}^{right} nums[i] - \sum_{i=0}^{left-1} nums[i]$.
By precomputing a prefix sum array `pref` of size $n + 1$ where `pref[k]` stores the sum of the first $k$ elements (with `pref[0] = 0`), any subsegment sum is computed in strictly $O(1)$ time as `pref[right + 1] - pref[left]`.

## Optimal approach

1. Create a prefix sum array `pref` of size $n + 1$, initialized with `pref[0] = 0`.
2. Iterate $i$ from 0 to $n - 1$:
   - Set `pref[i + 1] = pref[i] + nums[i]`.
3. For each query `[left, right]`:
   - Compute `sum = pref[right + 1] - pref[left]`.
   - Append `sum` to the results array.
4. Return the results array.

Complexity:
- Time: $O(n)$ preprocessing time to build the prefix array, plus $O(1)$ per query. Overall time is $O(n + q)$, which comfortably executes in under 10 milliseconds for $10^4$ queries.
- Space: $O(n)$ auxiliary space to store the prefix sum array `pref` of size $n + 1$.

## Code walkthrough

In the reference implementation:
- `vector<long long> pref(n + 1, 0);`: creates 1-indexed prefix sums with base `pref[0] = 0`.
- `pref[i + 1] = pref[i] + nums[i];`: accumulates prefix sums linearly.
- `pref[r + 1] - pref[l]`: computes the sub-array sum in $O(1)$ without conditional boundary checks for $left = 0$.
- `res.push_back(...)`: records the computed range sum for each query in sequential order.

## Test it out loud

- Single element array: `nums = [5], queries = [[0, 0]]`. `pref = [0, 5]`. Query returns `pref[1] - pref[0] = 5 - 0 = 5`.
- Array of zeros: `nums = [0, 0, 0], queries = [[0, 1], [1, 2]]`. `pref = [0, 0, 0, 0]`. Queries return `0 - 0 = 0`.
- Alternating signs: `nums = [10, -10, 10, -10]`, query `[0, 1]`. `pref = [0, 10, 0, 10, 0]`. Query `[0, 1]` gives `pref[2] - pref[0] = 0 - 0 = 0`.

## Follow-ups

- What if elements in `nums` can be updated dynamically? (LeetCode 307 - Range Sum Query Mutable):
  A prefix array requires $O(n)$ per update. Use a Binary Indexed Tree (Fenwick Tree) or Segment Tree to support both point updates and range queries in $O(\log n)$ time.
- How to extend this to 2D matrices? (LeetCode 304 - Range Sum Query 2D Immutable):
  Build a 2D prefix sum table using inclusion-exclusion: `pref[r+1][c+1] = matrix[r][c] + pref[r][c+1] + pref[r+1][c] - pref[r][c]`.
- What if range updates are performed before queries?
  Use a difference array where adding $v$ to range $[l, r]$ is recorded as $diff[l] += v$ and $diff[r + 1] -= v$, prefix summing once at the end.

## Common mistakes

- Sizing the prefix array as size $n$ instead of $n + 1$, requiring an awkward special case `if (left == 0)` to avoid negative indexing.
- Off-by-one errors with index boundaries: querying range $[left, right]$ requires `pref[right + 1] - pref[left]`, not `pref[right] - pref[left]`.
- Forgetting that integer sums can exceed 32-bit limits if constraints were slightly larger (good practice to use 64-bit integer types like `long long` for prefix tables).
