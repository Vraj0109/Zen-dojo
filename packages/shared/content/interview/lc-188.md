## Clarify first
- How many transactions are permitted? At most k transactions, where each transaction consists of one buy followed by one sell.
- Can we hold multiple shares at once? No, you may hold at most one share at any given time.
- What if k >= n / 2? Since at most n / 2 transactions can physically occur in n days, the transaction limit becomes inactive, reducing to unlimited transactions.
- What should be returned if no profit is possible? Return 0.

## Examples to say out loud
- Consider `k = 2`, `prices = [2, 4, 1]`:
  - Buy at 2, sell at 4 gives profit 2. Only 1 profitable transaction exists. Output: 2.
- Multiple peaks: `k = 2`, `prices = [3, 2, 6, 5, 0, 3]`:
  - Buy at 2, sell at 6 (profit 4).
  - Buy at 0, sell at 3 (profit 3).
  - Total profit: `4 + 3 = 7`. Output: 7.
- Decreasing sequence: `k = 2`, `prices = [7, 6, 4, 3, 1]`: Output: 0.

## Brute force
A brute force recursive backtracking approach tries all combinations of buying, selling, or holding across n days while tracking the count of completed transactions. Without memoization, this explores O(3^n) states. Dynamic programming with state `(day, transactions, holding)` takes O(n * k) time and O(n * k) space. Space can be compressed to O(k) using two 1D state arrays.

## The key observation
If `k >= n / 2`, the transaction constraint is completely non-binding because we can execute at most one trade every two days. In this case, the problem collapses to Best Time to Buy and Sell Stock II: simply collect every positive price difference `prices[i] - prices[i - 1]` greedily in O(n) time.
For general `k < n / 2`, we maintain two arrays of size `k + 1`:
- `buy[t]`: the maximum cash balance on the current day while holding a share during transaction `t`.
- `sell[t]`: the maximum profit on the current day after completing transaction `t`.
Transitions for each price `p`:
`buy[t] = max(buy[t], sell[t - 1] - p)`
`sell[t] = max(sell[t], buy[t] + p)`

## Optimal approach
1. Let `n = prices.size()`.
2. Check if `k >= n / 2`:
   - If true: greedy sum of all positive price rises `sum(max(0, prices[i] - prices[i - 1]))` and return immediately.
3. Allocate arrays `buy` of size `k + 1` initialized to `INT_MIN / 2` and `sell` of size `k + 1` initialized to 0.
4. For each price `p` in `prices`:
   - For `t` from 1 to `k`:
     - `buy[t] = max(buy[t], sell[t - 1] - p)`
     - `sell[t] = max(sell[t], buy[t] + p)`
5. Return `sell[k]`.

Complexity:
- Time complexity: O(n * k) because for each of the n days we update k transaction levels in O(1) time. When `k >= n / 2`, it runs in O(n) time.
- Space complexity: O(k) auxiliary space for the two arrays of size `k + 1`.

## Code walkthrough
- `if (k >= n / 2)`: Prevents running large O(n * k) DP loops when k is large, eliminating memory limits and executing in O(n).
- `vector<int> buy(k + 1, INT_MIN / 2), sell(k + 1, 0)`: Compact state representation where `sell[0] = 0` provides the initial zero-profit base.
- `buy[t] = max(buy[t], sell[t - 1] - p)`: Purchases share `t` using capital gained after selling transaction `t - 1`.
- `sell[t] = max(sell[t], buy[t] + p)`: Sells share `t` at current price `p`.
- Returns `sell[k]`.

## Test it out loud
- Test `k = 1, prices = [1, 5, 2, 8]`:
  - `n = 4, k = 1 < 2`.
  - Day 1 (p = 1): `buy[1] = -1`, `sell[1] = 0`.
  - Day 2 (p = 5): `buy[1] = -1`, `sell[1] = 4`.
  - Day 3 (p = 2): `buy[1] = max(-1, -2) = -1`, `sell[1] = 4`.
  - Day 4 (p = 8): `buy[1] = -1`, `sell[1] = max(4, -1 + 8) = 7`.
  - Returns 7. Correct.
- Test `k = 2, prices = [1, 5, 2, 8]`:
  - `k = 2 >= 4 / 2 = 2`.
  - Greedy path adds `(5 - 1) + (8 - 2) = 4 + 6 = 10`. Returns 10. Correct.

## Follow-ups
- Why is the `k >= n / 2` shortcut important? Without this check, test cases where `k = 10^9` would allocate massive arrays and cause Out Of Memory (OOM) errors or unnecessary computation.
- What if there was a transaction fee per sale? Deduct the fee from `sell[t] = max(sell[t], buy[t] + p - fee)`.

## Common mistakes
- Allocating a full `n x k` matrix when space can be compressed to `2 x k` or two 1D vectors of size `k + 1`.
- Omitting the `k >= n / 2` optimization, which causes timeouts and memory limits on large k inputs.
- Initializing `buy` array to 0, which incorrectly assumes you can purchase without incurring a negative cash flow.
