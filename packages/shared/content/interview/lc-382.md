## Clarify first

- Is the linked list length known in advance? (No, singly linked lists do not provide length in $O(1)$ without an initial traversal).
- What should be the probability distribution? (Every node must have an identical, uniform probability $1/N$ of being chosen).
- What are the memory constraints? (The interviewer typically evaluates Reservoir Sampling to achieve true $O(1)$ extra space, without copying all elements into an array).
- Can the list be empty? (Constraints guarantee at least 1 node; $1 \le N \le 10,000$).
- Can node values be negative? (Yes, $-10,000 \le Node.val \le 10,000$).

## Examples to say out loud

- Single node: `head = [1]`. `getRandom()` returns 1 with $100\%$ probability.
- Two nodes: `head = [1, 2]`.
  - Start with `ans = 1`.
  - Node 2 is visited ($i = 2$): probability of picking node 2 is $1/2$.
  - Both 1 and 2 are returned with probability $0.5$.
- Three nodes: `head = [1, 2, 3]`.
  - Node 3 ($i = 3$): replaces reservoir with probability $1/3$.
  - Node 1 or 2 survived step 2 with probability $1/2$, and survives step 3 with probability $2/3 \implies \frac{1}{2} \times \frac{2}{3} = \frac{1}{3}$. Every element has probability $1/3$.

## Brute force

A naive approach traverses the linked list during the constructor and copies all $N$ values into an `std::vector<int>`. Then `getRandom()` calls `rand() % values.size()` in $O(1)$ time. While fast for repeated queries, this consumes $O(N)$ extra space. If the linked list is massive (e.g. Billions of elements streaming across a network), storing the entire list in memory is impossible.

## The key observation

We use **Reservoir Sampling** (Alan G. Waterman's Algorithm R), which samples from a stream of unknown or unbounded length in $O(1)$ extra space.
- Set the initial candidate answer to the head value: `ans = head->val`.
- For the $i$-th node visited ($i = 2, 3, \dots, N$), generate a random integer in $[0, i - 1]$. If the random value is 0 (which occurs with probability $1/i$), replace `ans` with `curr->val`.
- Mathematical induction:
  - The $k$-th element is selected at step $k$ with probability $1/k$.
  - For each subsequent step $j > k$, it is NOT replaced with probability $1 - 1/j = \frac{j-1}{j}$.
  - The overall probability that element $k$ is the final choice after $N$ elements is:
    $\frac{1}{k} \times \frac{k}{k+1} \times \frac{k+1}{k+2} \times \dots \times \frac{N-1}{N} = \frac{1}{N}$.

## Optimal approach

1. Constructor `Solution(head)`:
   - Store the pointer to the `head` of the linked list.
2. Operation `getRandom()`:
   - Initialize `ans = head->val`.
   - Set pointer `curr = head->next` and counter `i = 2`.
   - While `curr != nullptr`:
     - If `rand() % i == 0`:
       - Overwrite `ans = curr->val`.
     - Advance `curr = curr->next`.
     - Increment `i++`.
   - Return `ans`.

Complexity:
- Time: $O(1)$ initialization; $O(n)$ time per `getRandom()` call, where $n$ is the number of nodes in the linked list.
- Space: $O(1)$ auxiliary space since only a few pointer and integer counter variables are used.

## Code walkthrough

In the reference implementation:
- `int ans = head->val;`: initializes the reservoir with the first element (guaranteed $100\%$ if $n = 1$).
- `int i = 2;`: tracks the 1-based index of the candidate element currently being evaluated.
- `if (rand() % i == 0) ans = curr->val;`: simulates a Bernoulli trial with success probability $1/i$.
- `curr = curr->next; i++;`: advances through the single linked list stream sequentially.

## Test it out loud

- Single node: `[42]`. Loop condition `curr = head->next` is null. Loop does not execute; returns 42.
- Large list: `[1, 2, ..., 10000]`. Traverses through all nodes, dynamically updating the reservoir without requiring multiple passes or knowing length upfront.
- Negative numbers: `[-10]`. Values pass through untouched, returning $-10$.

## Follow-ups

- What if $k$ random nodes need to be chosen instead of 1?
  Maintain an array reservoir of size $k$. Fill the reservoir with the first $k$ elements. For element $i > k$, pick a random integer $r \in [0, i - 1]$; if $r < k$, replace `reservoir[r]` with the new element.
- What if `getRandom` is called much more frequently than list updates, and memory is available?
  Cache all elements into a vector in $O(n)$ time and $O(n)$ space; `getRandom` then runs in strictly $O(1)$ time per call.
- What if nodes arrive across a distributed cluster?
  Assign each item a random priority $u \sim \text{Uniform}(0, 1)$, and take the item with the maximum priority.

## Common mistakes

- Using `rand() % (i + 1)` instead of `rand() % i`, distorting the replacement probability away from $1/i$.
- Assuming the list length can be measured without a traversal.
- Trying to choose a random index $r \in [0, n - 1]$ by first walking the list to count $n$, which requires two passes over the list instead of a single stream pass.
