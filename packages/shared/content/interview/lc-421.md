## Clarify first
- Can `i` and `j` be the same index? Yes, `nums[i] XOR nums[i] = 0` is valid.
- Are numbers non-negative? Yes, values are between 0 and 2^31 - 1, fitting in non-negative 32-bit integers.
- How large is the input array? Up to 200,000 numbers, which requires an algorithm faster than O(n^2).
- Can the answer be zero? Yes, if all elements are identical or there is only one element.

## Examples to say out loud
- Consider `nums = [3, 10, 5, 25, 2, 8]`:
  - In binary: `5 = 00101_2`, `25 = 11001_2`.
  - `5 XOR 25 = 11100_2 = 28`.
  - No other pair yields a larger XOR, so the answer is 28.
- Single number: `nums = [7]`. `7 XOR 7 = 0`.
- All equal numbers: `nums = [5, 5, 5]`. XOR of any pair is 0.

## Brute force
A brute force approach computes `nums[i] ^ nums[j]` for all pairs `0 <= i <= j < n` and takes the maximum. With n up to 200,000, checking all pairs takes O(n^2) operations, which requires roughly 2 * 10^10 operations and times out. We need a bit-by-bit approach that takes advantage of binary representation.

## The key observation
To maximize XOR, higher bits are strictly more valuable than all lower bits combined. If bit 30 can be set to 1, any solution with bit 30 set will exceed all solutions where bit 30 is 0.
Thus, we can greedily decide the answer bit-by-bit from bit 30 down to bit 0:
Suppose we have determined the best prefix for the first several bits, denoted as `best`. For the current bit, we test whether setting this bit to 1 is possible by setting `cand = (best << 1) | 1`.
By algebraic property of XOR:
`a ^ b = cand` is equivalent to `a ^ cand = b`.
Therefore, `cand` is achievable if and only if there exist two prefixes `a` and `b` in our set such that `(cand ^ a)` is present in the set of prefixes. If such a match exists, we keep the 1 bit; otherwise, we must set that bit to 0 (`best << 1`).

## Optimal approach
1. Initialize `best = 0`.
2. Iterate `bit` from 30 down to 0:
   - Extract the prefixes of all numbers truncated to the current bit: `prefix = x >> bit`. Store them in a hash set.
   - Formulate candidate XOR prefix: `cand = (best << 1) | 1`.
   - Check if there exists any prefix `p` in the set such that `cand ^ p` is also in the set.
   - If true: `best = cand` (we can achieve a 1 at this bit).
   - If false: `best = best << 1` (we must accept a 0 at this bit).
3. After evaluating bit 0, return `best`.

Complexity:
- Time complexity: O(31 * n) = O(n) because for each of the 31 bit positions, inserting all n prefixes into a hash set and querying takes O(n) time.
- Space complexity: O(n) auxiliary space to store up to n prefixes in the hash set at each bit level.

## Code walkthrough
- `for (int bit = 30; bit >= 0; bit--)`: Inspects bits from most significant to least significant.
- `unordered_set<int> prefixes`: Collects `x >> bit` for all numbers in `nums`.
- `int cand = (best << 1) | 1`: Greedily tests whether the next bit can be 1.
- `if (prefixes.count(cand ^ p))`: Verifies if complementary prefix exists using `a ^ b = c <=> a ^ c = b`.
- `best = ok ? cand : best << 1`: Locks in 1 if achievable, otherwise shifts with 0.
- Returns `best`.

## Test it out loud
- Test `nums = [1, 2]`:
  - In binary: `1 = 01_2`, `2 = 10_2`.
  - At bit 1: prefixes `{0, 1}`. `cand = 1`. `1 ^ 0 = 1` which is in prefixes. `best = 1`.
  - At bit 0: prefixes `{1, 2}`. `cand = (1 << 1) | 1 = 3`. `3 ^ 1 = 2` which is in prefixes! `best = 3`.
  - Return 3 (`1 ^ 2 = 3`). Correct.
- Test `nums = [5, 5, 5]`:
  - For all bits, prefixes only contain a single value `p`. `cand ^ p` can never equal `p` when candidate has trailing 1. Candidate is never valid; returns 0. Correct.

## Follow-ups
- Can this be implemented using a Binary Trie? Yes, inserting all 31-bit binary representations into a Trie of height 31 allows querying the maximum XOR for each number by greedily following opposite branch bits (if available), running in O(31 * n) time and O(31 * n) space.
- Why is the hash set approach often faster in practice? The hash set avoids pointer allocations and node overhead of a Trie, maintaining lower constant factors and cache locality.

## Common mistakes
- Iterating bits from 0 up to 30 instead of 30 down to 0, which violates the greedy property that higher bits dominate lower bits.
- Forgetting that `cand ^ p` tests XOR consistency because `a ^ b = c` implies `a ^ c = b`.
